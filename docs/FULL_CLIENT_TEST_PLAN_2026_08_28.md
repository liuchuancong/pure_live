# Pure Live Android / Windows 全面实机测试计划（2026-08-28）

## 1. 目的与范围

本计划用于当前 `master` 的 Android 手机与 Windows x64 客户端实测、故障定位、修复回归和资源趋势核验。测试顺序固定为：已连接 Android 时先完成 Android；Android 阶段结束后再串行进行 Windows。重型测试、构建和打包遵守 `BUILD_POLICY.md`，Android 与 Windows 不并发构建。

本轮覆盖四层证据：

1. **静态合同**：页面入口、状态机、异步代次、订阅/Timer/播放器/录制资源释放、设置迁移和平台数据契约。
2. **确定性自动化**：受影响单元测试、Widget 测试、接口 fixture、设置持久化和生命周期回归。
3. **真实客户端操作**：Android ADB 实机和 Windows 本机窗口中的全部可操作页面、按钮、手势、模式切换与错误提示。
4. **运行趋势**：启动耗时、首页稳定、帧体验、CPU、内存、线程/句柄、网络恢复、长时间播放/弹幕/录制。

“通过”只代表对应案例和证据层成立。外部平台接口随时间变化；未登录平台、当前没有可用直播样本或缺少对应系统设备时，在报告中保留具体证据缺口。

## 2. 被测基线与证据目录

每次测试开始冻结以下信息：

- Git 完整 SHA、分支、工作树状态、上游/维护分支相对关系；
- App 语义版本、build number、包名、ABI、Flutter/Gradle/Windows 工具链版本；
- Android：设备序列号、型号、Android 版本、分辨率、密度、支持刷新率、当前刷新率、电量、温度、包版本；
- Windows：系统版本、显示器分辨率/缩放/最高刷新率、GPU、播放器内核、数据目录；
- 设置快照：主题、刷新率、导航、播放器、画中画、弹幕、本地互动、录制和平台登录状态。改变设置的案例结束后恢复快照；不修改真实账号 Cookie、关注关系和云端数据。

证据统一写入：

```text
local-artifacts/diagnostics/full-regression-20260828/
  android/{baseline,home,search,settings,playback,pip,record,fault,perf}/
  windows/{baseline,home,search,settings,playback,pip,record,fault,perf}/
  reports/
```

每个案例至少记录 `case-id`、开始/结束时间、步骤、期望、实际、截图/日志路径、资源采样和结论。日志先过滤 Cookie、令牌、用户输入和私有直播地址。

## 3. 严重程度与放行标准

| 级别 | 定义 | 处理 |
| --- | --- | --- |
| P0 | 启动失败、普遍黑屏、数据破坏、安装/升级破坏、播放器或录制主链路整体失效 | 立即停止后续发布链，定位首个错误状态 |
| P1 | 稳定复现的卡死、暂停、弹幕停更、模式切换损坏、主平台接口失效、资源持续无界增长 | 修复并重跑受影响矩阵及相邻模式 |
| P2 | 单页面功能、排序、布局、交互、文案或特定平台兼容错误 | 记录根因后定向修复与回归 |
| P3 | 低频视觉细节、证据不足或外部数据偶发现象 | 记录样本和后续条件 |

阶段放行条件：

- 启动、返回、首页导航、直播播放、弹幕、画质/线路、前后台、横竖屏、小窗、录制没有 P0/P1；
- 页面横向列表有边界，纵向列表能跟手滚动，刷新状态不会造成卡片乱跳或重复请求风暴；
- 无用户操作时不调用暂停/停止；模式切换后的播放器、弹幕会话和录制状态只保留一个有效代次；
- 退出直播/关闭小窗/停止录制后，Timer、Stream、WebSocket、纹理、FFmpeg 会话和页面 Controller 被取消或复用到明确所有者；
- 同一平台不同房间之间不串弹幕、不重复死循环，不接纳上一会话的迟到事件；
- CPU/内存以基线和趋势判断，不以单个瞬时值代替结论；长测结束后资源能够回落或进入稳定平台。

- [ ] A0-01 冻结 SHA、版本、设备和设置快照。

### A1 — Android 安装、升级与冷启动

- [ ] AND-BASE-01 显式选择一个 ADB transport；当同一手机出现两个无线序列时，所有命令固定传 `-s SERIAL`，避免装到一个 transport、采样另一个 transport。
- [ ] AND-BASE-02 核对已装 APK 包名、版本、ABI、签名类型和数据目录；覆盖安装前后关注、历史、标签、主题和核心设置保持。
- [ ] AND-BASE-03 强制停止后冷启动 5 次：没有白屏/黑屏/闪退/重复页面；启动期间首页数据开始刷新且不会阻塞首帧。
- [ ] AND-BASE-04 热启动 5 次、后台 5 秒/20 秒/2 分钟恢复；检查旧直播状态刷新、页面位置和播放器行为。
- [ ] AND-BASE-05 系统侧滑返回、应用返回键、Home 键和任务切换；首页返回进入后台，二级页逐层返回，直播页按产品规则退出。
- [ ] AND-BASE-06 采集启动 logcat、ANR/crash、首帧时间、进程 CPU/PSS、线程数、电量和温度。

### A2 — Android 首页、卡片、导航与刷新

- [ ] AND-HOME-10 录制中心状态 Tab 横向边界、任务列表纵向边界、空态、打开目录和设置入口。

- [ ] 房间详情、开播状态、标题、主播、封面、关注状态；

- [ ] 画质原始标签、标准化中文标签、quality id、默认/最高选择准确性；
- [ ] 线路数量、cursor/id、请求头/Cookie、最终播放地址；
- [ ] 播放地址有效期、重定向、协议、解码能力与刷新策略；
- [ ] 弹幕匿名/登录要求、WebSocket 地址、心跳、重连和房间隔离；
- [ ] 录制地址是否与播放地址合同不同，FFmpeg 需要的 headers、协议白名单、时间戳和容器兼容。

每个平台至少完成一个当前在播样本的详情/播放/画质/线路/弹幕/录制探测；缺少直播样本时保留 fixture 自动化与探测时间，不借用另一平台结论。

### A7 — Android 录制、后台与本地互动

- [ ] AND-REC-01 从直播页开始录制，录制中心立即出现正确房间、平台、画质、状态、时间、实时大小、速度和码率。
- [ ] AND-REC-02 停止、取消等待、失败重试、立即检查、重连；状态只按允许路径转换，不全部显示“等待开播”。
- [ ] AND-REC-03 Bilibili/斗鱼/虎牙/抖音/快手/YY/CC/Twitch/SOOP/IPTV 的流地址和 headers 分别核验；有可用样本才执行短录制。
- [ ] AND-REC-04 录制文件可由 ffprobe 读取，持续时间接近墙钟，文件大小增长；0B、超大时长、负速度和错误阶段不出现。
- [ ] AND-REC-05 录制设置：目录、缓存上限、默认画质、拼音目录、最佳流、读写超时、队列、分段、最大任务、重连、轮询/退避和开机启动。
- [ ] AND-REC-06 录制中心横/纵滚动边界、卡片自适应列数、长错误文本、任务删除确认、重启后持久化恢复。
- [ ] AND-BG-01 后台播放和 ASMR 分开建模；关闭 ASMR 后普通直播不显示音频状态，耳机/投屏/小窗各自语义唯一。
- [ ] AND-BG-02 前台服务通知、音频焦点、系统省电提示、网络切换后恢复；不承诺绕过系统厂商的强制终止，但应用内部状态可恢复。
- [ ] AND-LOCAL-01 各平台本地资源包、头衔/等级/礼物效果、金币扣减、历史和设置持久化；明确仅在本地展示。

### A8 — Android 故障注入、性能与稳定性

- [ ] AND-FAULT-01 飞行模式/断网 10–30 秒后恢复；首页请求、直播、弹幕、录制采用有限退避且页面可手动恢复。
- [ ] AND-FAULT-02 Wi-Fi↔蜂窝网络语义 fixture、DNS 错误、HTTP 超时、429、5xx、空响应、字段类型漂移；错误分类明确。
- [ ] AND-FAULT-03 流地址过期、CDN 重定向、解码错误、线路失效；只在明确错误时恢复，不以固定延时自动暂停。
- [ ] AND-FAULT-04 快速进入/退出房间 20 次、A/B 房间切换 20 次、横竖屏/小窗循环 20 次；无崩溃、ANR 和旧会话回流。
- [ ] AND-PERF-01 首页静置 10 分钟、列表滑动 5 分钟、播放+弹幕 30 分钟、画中画 15 分钟、录制 15 分钟的 CPU/PSS/线程/温度趋势。
- [ ] AND-PERF-02 页面退出后 60 秒资源回落；重复 10 次后增量不持续线性上升。图片区缓存、弹幕队列和历史列表有明确上限。
- [ ] AND-PERF-03 60/90/120Hz 模式实时生效；省电/均衡/最高档的帧策略和小窗/覆盖弹幕 FPS 合同一致，耗电提示准确。
- [ ] AND-PERF-04 采集 `gfxinfo framestats`、CPU、meminfo、线程和热状态；以 P50/P90/P95/P99 和 jank 数量比较基线与修复后。

## 6. 修复与回归规则

1. 复现后先写 `provenance`：`upstream-existing`、`fork-regression`、`integration-conflict`、`external-drift`、`environment-or-data` 或 `not-reproduced`。
2. 找到第一个错误状态和所有者；不以增加任意延时、无限刷新、全局重建或无限重试掩盖问题。
3. 先补确定性回归，再做最小修复；播放器来源、自动恢复、几何、录制分开提交并可独立回滚。
4. 修改完成后只跑受影响测试；代码稳定后执行一次 Analyze。重型命令通过资源守卫串行执行。
5. Android 修复后重新安装来自当前 SHA 的 APK，重跑原案例、相邻模式和资源回落；随后才进入 Windows。
6. 每个结果标记 `pass`、`fail`、`blocked-by-sample`、`external-drift` 或 `not-run`，并附证据路径。

## 7. 最终报告结构

- 构建/安装基线和 SHA；
- Android 逐阶段通过/失败/样本缺口数量；
- Windows 逐阶段通过/失败数量；
- 新发现问题：来源、根因、修复提交、回归证据；
- 平台接口能力矩阵和探测时间；
- CPU、内存、线程、句柄、帧时间和温度对比；
- 未覆盖平台/登录态/直播样本和剩余风险；
- 本轮实际产物路径、哈希，以及是否进入正式发布阶段。
