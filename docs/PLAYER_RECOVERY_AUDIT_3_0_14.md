# Pure Live v3.0.14 播放器与录制恢复审计

审计日期：2026-08-27

审计范围：播放 URL、来源代次、原生事件、音视频解码、线路与播放器内核回退、页面状态、小窗生命周期，以及录制 URL 轮换与 FFmpeg 故障分类。

问题来源：`fork-regression`、既有生命周期缺口与第三方原生播放器环境差异的组合。本轮不合并上游、不连接或操作手机；修改建立在当前维护分支、第三方播放器源码语义和确定性回归之上。

## 1. 已确认的根本原因

1. **恢复所有权分裂**：适配器直接发布/重置，管理器同时换线路/内核，页面又在 `play` 返回后强制写入“播放中”，三个状态源会互相覆盖。
2. **来源事件没有代次**：保留同一原生播放器切换房间、画质和 CDN 时，旧来源的尺寸、播放、错误回调会进入新页面。
3. **同 URL 重开被错误去重**：软件解码回退必须用同一 URL 重新打开，但 MediaKit 适配器提前返回；此时管理器已经重置公开状态，因此界面永久停在空白或加载中。
4. **原生日志被当作终止事实**：mpv 的硬件解码尝试、坏包、音频与视频错误共用日志通道；仅凭包含 `decoder`/`io` 等片段会误判类别，也会在 mpv 自行恢复前过早切换。
5. **打开与首帧没有独立截止时间**：原生 `open/setupDataSource` Future 卡住时，恢复事件被串行队列挡在后面；打开成功但没有解码帧时又会无限加载。
6. **内核切换不是事务**：新内核初始化或监听绑定失败可能留下半安装播放器，旧播放器监听已被清理，后续回退失去状态。
7. **录制错误分类过宽**：斗鱼等平台的“输入无法打开”被统一翻译为 URL 格式错误；重试只覆盖部分线路，没有跨清晰度轮换。

## 2. 新恢复状态机

顺序固定为：

`当前来源确认 → 可恢复日志观察窗口 → 当前 URL 软件视频解码一次 → 可用线路轮换 → 播放器内核轮换 → 发布一次最终错误`

- `SourceEventFence` 为每次打开生成代次，只接收当前原生 `path` 所属事件。
- 错误携带稳定 `code` 和音频/视频组件；音频错误不触发视频软件解码。
- MediaKit 的宽高仅作为画面几何元数据，首帧就绪使用原生解码帧/音频参数；旧房间几何缓存不再跨来源复用。
- 原生打开有 18 秒上限；打开后仍无可播放帧有独立上限。任何阶段都不会无限占住生命周期队列。
- Fijk 与 BetterPlayer 在调用原生打开前启用来源监听，保留同步错误；Fijk 请求头和 User-Agent 的异步设置全部等待完成。
- 自动内核切换先完整建立新播放器与监听，再释放旧播放器；安装失败时恢复旧引用并继续剩余内核。

## 3. 录制增强

- 每轮解析收集全部清晰度和 CDN，按“清晰度选择 ID + 去签名参数后的线路身份”去重；失败后跨线路、跨清晰度轮换。
- FFmpeg 故障分为输出目录、命令、HTTP 权限、传输、输入打开、输入格式、解码和原生类别；输出/命令错误停止盲目重试，其余按录制策略刷新 URL。
- 原生 FFmpeg 归档由锁文件版本选择受审查 profile，并验证 SHA-256；避免 Dart 包与 Android/Windows 二进制版本漂移。

## 4. 回归合同

- 连续来源失败会依次经过下一线路和下一内核，中间错误不进入页面。
- 同 URL 硬解失败必须实际执行第二次打开，且只执行一次软件视频解码。
- 音频解码失败直接进入下一内核，不修改视频硬解策略。
- 原生打开 Future 卡住、打开后无播放帧、旧来源晚到回调均在有界时间内结束或被丢弃。
- 小窗关闭与同房间恢复不依赖后台继续产生 vsync，房间快照只消费一次。
- 录制候选、失败类别、重试性与用户可见文案均有确定性单元测试。

## 5. 证据边界

应用能够消除自身状态竞争、实施软硬解码/线路/内核回退并输出稳定诊断；它不能让设备不存在的 codec、已经损坏的直播数据、失效凭据或地区受限 CDN 变成可解码内容。正式门禁覆盖静态分析、全量测试、公开接口探测、仓库审计和 APK 原生库/ABI/签名；用户设备上的特定厂商 MediaCodec 行为仍需安装后的实际样本日志确认。
