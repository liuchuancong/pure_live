# 桌面退出弹窗与动作事务审计

## 范围与结论

本轮以 `21372d14` 为基线，代码修订提交为 `9f463efb`。范围限桌面窗口关闭确认、退出/最小化动作、退出偏好持久化与当前/旧版备份字段，以及共用中英文文案；未构建 Windows 或 Android 候选，未执行原生 Windows GUI、ADB 或设备操作，Astra Light 使用 **0 次**。

旧实现存在四组可验证缺口：

1. `exitChoose` 默认值为空字符串，通用设置中的“不再确认退出”即使开启，也没有稳定的默认动作；损坏或未知动作也缺少统一回落值。
2. `exit_app` 同时承担托盘菜单/按钮标签，却保存了完整确认句，导致动作标签冗长且语义重复。
3. 320×480、3.0 倍英文文字下，退出确认弹窗稳定产生 **224 px 底部溢出**；动作和复选框缺少统一的窄屏可达合同。
4. 两个动作会先改偏好再启动原生操作，最小化还是延迟且未等待；路由以空结果关闭，并发关闭可叠加弹窗，原生失败也没有偏好和窗口状态回滚。

`9f463efb` 将以上路径收敛为一个可等待、可回滚的桌面退出事务。A2-01 获得新的源码与确定性回归证据，但 Windows 当前候选的真实关闭、托盘和窗口管理器行为仍待同一 GUI 批次验证，因此状态保持 `RUN`。

## 动作与持久化合同

`ExitSettingsController` 现在声明稳定动作键：

- `exit`：默认动作；
- `minimize`：最小化或隐藏到托盘；
- 其余字符串、非字符串和缺失字段统一归一化为 `exit`。

归一化入口覆盖 Hive 启动修复、运行时写入、`toJson`、当前备份 `parseConfig` 和旧版备份 `extractConfig`。因此首次开启“不再询问”、导入旧备份或遇到损坏字段时均有同一个确定结果。托盘菜单和确认按钮使用简短动作标签 `Exit` / `退出应用`，确认问题继续由 `confirm_exit` 独立表达。

## 路由、布局与并发

退出弹窗改为独立的有状态路由组件：

- `AlertDialog.scrollable` 让标题、正文和复选框在窄视口内滚动；
- 水平/垂直边距固定为 16/20，正文最大宽度为 420；
- 动作空间不足时向下排列，退出与最小化按钮的最小命中尺寸均为 48×48；
- 动作使用弹窗所属 `BuildContext` 返回带动作和“不再询问”状态的类型化结果；系统返回产生 `null` 并映射为 `false`；
- 静态 single-flight 让同一时刻的多个关闭请求共享一个路由和一个最终结果。

在 320×480、3.0 倍英文文字夹具中，两个动作持续位于视口内，复选框可滚动到达并可选中，未再出现布局异常。

## 原生动作与失败恢复

选择结果先通过 `HivePrefUtil.persistBatch` 等待偏好落盘，再执行原生动作；只有原生动作完成，调用方才得到 `true`。原生失败时：

1. 新选择的“不再询问”和动作键恢复到操作前值；
2. 已关闭的窗口拦截恢复；
3. 原先可见但已隐藏的窗口重新显示并聚焦；
4. Bilibili Web 登录浮层状态恢复；
5. 用户收到本地化的窗口动作失败提示，调用方得到 `false`。

已记忆动作失败时会重新启用下次确认。Windows/Linux 的最小化路径在关闭拦截开启时隐藏到托盘，拦截关闭时调用原生 `minimize`；macOS 继续最小化到 Dock。桌面销毁错误不再被吞掉，使上层事务可以执行恢复。
