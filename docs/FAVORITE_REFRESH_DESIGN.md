# 关注页刷新与状态一致性设计

## 目标

关注页同时满足四个约束：

1. 手机端每个平台页都能下拉，短列表和空列表也有清晰动画；
2. 启动、回前台、定时器、手动下拉不会并发覆盖彼此；
3. 缓存只用于标题、封面和稳定布局，不把上次进程的开播位当成当前事实；
4. 一轮网络核验只发布一次最终快照，卡片不会按请求完成顺序反复跳位。

## 已确认的旧链路问题

### 下拉手势没有进入刷新状态

`EasyRefresh` 包在 `TabBarView` 的平台子页内是正确方向，但子 `GridView` / `CustomScrollView` 又显式使用
`PureLiveScrollPhysics`。Android 上它把 `ClampingScrollPhysics` 放在物理链外层，边界位移在到达
EasyRefresh 之前已被消费，所以静态测试能直接调用 `onRefresh`，真实手指下拉却看不到动画，也不会触发任务。

当前规则：

- 每个平台子页拥有独立 `EasyRefresh.builder`；
- `triggerAxis` 固定为纵向，避免与平台横滑竞争；
- builder 提供的 physics 必须直接安装到当前唯一纵向 ScrollView；
- 空列表继续使用同一条链路，Material 刷新头在 72 px 释放时触发。

### 平板横屏被宽度误判为桌面

旧的关注网格在 `width > 680` 时直接跳过逐平台 `EasyRefresh`。这只能描述可用布局宽度，不能描述输入设备：Android/iOS 平板横屏同样会超过 680 px，但仍使用触控手势。由于关注页外层刷新器已经为嵌套 `TabBarView` 主动关闭，内层再按宽度关闭后整条刷新链消失。

当前规则：

- 移动平台无论横竖屏、平板或分屏宽度都保留逐平台下拉刷新；
- 桌面宽屏使用分页、重试按钮和键盘入口，不额外包装移动刷新；
- 窄桌面窗口沿用紧凑布局和触控/鼠标拖动刷新；
- 宽度只决定网格列数、卡片尺寸和缓存范围，不再单独决定刷新交互。

### 启动核验被恢复事件取消

旧实现每开始一轮刷新就递增 `_refreshEpoch`。冷启动全量核验尚未完成时，生命周期 resumed 的 450 ms
定时任务会开始第二轮并使第一轮结果失效。第二轮又不是“未核验即未知”模式，因此请求失败的房间继续保留
旧开播状态。这解释了首页显示在播、进入房间重新取详情后才提示下播的确定性差异。

当前规则：

- 刷新事务通过单锁串行；`_refreshEpoch` 只用于控制器销毁后的取消；
- 启动核验存在时，恢复、定时和事件刷新直接复用这次全量结果；
- 手动下拉、启动和超过新鲜度阈值的恢复刷新绕过失败冷却，用户操作不会被五分钟静默跳过；
- 网络任务仍采用有界并发，结果全部结束后再进行一次 Hive 写入和一次界面发布。

## 启动视觉状态机

1. 读取持久关注；
2. 生成仅存在于内存的 verification preview：标题、封面、标签、排序值保留，状态统一为 unknown；
3. preview 继续留在上次所属的“直播 / 录播 / 未开播”位置，卡片显示“正在核验”，避免首屏清空和乱跳；
4. 平台请求并发执行；成功结果使用服务器状态，失败结果保留 unknown；
5. 一次性提交最终快照；unknown 卡片显示“状态待确认”，手动下拉可立即重试。

## 平台返回语义

- Bilibili、Douyu、Huya、Kuaishou 使用轻量房间元数据接口，不为首页准备播放签名或弹幕凭据；
- CC、Twitch、SOOP 的关注刷新路径向控制器传播传输和结构异常，不再把异常包装为离线；
- SOOP 的明确无直播码映射为 offline，屏蔽码映射为 banned，登录/会话异常映射为刷新失败；
- Huya `REPLAY` 标记为录播，不混入当前直播排行；
- 平台返回临时或规范房间号时，刷新结果仍绑定发起请求的收藏身份，防止标签、Key 和合并目标断开。

## 回归约束

- Widget 测试必须用真实 pointer drag 验证刷新动画和回调，直接调用 callback 不构成下拉刷新证据；
- 判定测试必须覆盖宽屏移动、宽屏桌面与窄桌面，阻止响应式阈值再次覆盖平台输入语义；
- 启动策略测试覆盖 live / replay / offline 三个 preview 分桶及全部 unknown；
- 合并测试覆盖平台返回不同规范房间号的情况；
- 新平台若会在 `getRoomDetail` 内吞掉网络异常，应实现 `LiveSiteRoomRefresher` 严格路径。
