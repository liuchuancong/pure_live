# Pure Live v3.0.15 播放器回归修复审计

审计日期：2026-08-27

问题来源：`fork-regression`。没有合并上游代码；回归由 v3.0.14 的播放器恢复改动引入。

## 1. 第一个错误状态

v3.0.14 在复用 MediaKit 原生播放器时同时增加了三项硬条件：

1. 原生 `path` 必须与请求 URL 完全相等；
2. Android/libmpv 必须提供 `video-frame-info/picture-type` 或 `estimated-vf-fps`；
3. 只有以上条件成立，原生 `playing=true`、`videoParams` 和缓冲结束事件才允许进入公共状态。

实际直播地址会被 CDN 重定向、协议层重写或规范化；部分 Android 后端也不提供这些可选帧属性。更关键的是，首个播放、尺寸和帧事件可能在 `Player.open` 返回前到达，此时来源栅栏仍处于 opening 状态，事件先被丢弃。打开完成后的状态回读又被相同硬条件拦截，当前来源因此永久缺少播放和几何证据。

## 2. 连锁影响

- `PlayerManager` 收不到 `playing=true`，把已播放直播继续视为未就绪；
- 适配器 10 秒与管理器 12 秒计时器分别制造来源错误并重开线路/内核；
- 用户侧表现为自动暂停、反复加载、黑屏或解码失败；
- 当前 `videoParams` 被拦截后，竖屏识别和主动内容探测没有输入，普通页、全屏和小窗同时退回错误比例；
- 自动化只模拟了 URL 完全相等且首帧属性存在的理想顺序，因此没有覆盖真实 Android 分支。

## 3. 修复设计

- 来源代次只负责隔离 replacement open 进行中的事件和失效代次；open 完成即接收当前原生播放器事件。
- 原生 path 仅作为诊断信息，不参与播放授权。重定向、规范化和没有 path 回调都属于合法状态。
- `Player.stream.playing` 是公共播放状态的权威。首帧属性只增加诊断证据，不得否决 native playing。
- 删除适配器内部的无帧超时，并把管理器默认推测式就绪超时关闭。明确的 open 异常和原生错误仍进入既有有界恢复。
- open 完成后回读播放器快照；成对 `videoParams` 立即进入当前几何代次，之后由既有稳定器和主动内容探测决定竖屏内容比例。

## 4. 回归合同

- 原生 URL 与请求 URL 不一致时，open 完成后的播放和尺寸事件继续有效；
- 原生没有 path 回调时，当前代次继续有效；
- 缺少可选 mpv 帧属性时，`playing=true` 仍发布播放状态；
- 可选帧属性本身不得制造虚假的播放状态；
- 默认策略不会仅因慢流暂时没有 playing 事件而重开线路或内核；
- 当前来源的 `720×1280` 解码尺寸会稳定提交为竖屏，不复用上一来源几何。

## 5. 回滚与证据边界

- 修改前状态保存在本地分支 `recovery/v3.0.14-broken`，v3.0.13 仍是播放器子系统的上一稳定比较点。
- 自动化覆盖事件顺序与几何状态机；本轮遵循用户要求，不连接或操作手机。特定厂商 MediaCodec、地区 CDN 和登录流仍由安装后的实际样本形成独立证据。
- 后续播放器改动按“来源隔离、播放状态、解码诊断、几何呈现、录制”分批提交和验证，不再把多个生命周期不变量合并为一个大提交。
