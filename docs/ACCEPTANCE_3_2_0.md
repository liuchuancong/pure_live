# 3.2.0 完整验收入口

本页只负责执行顺序和门禁。当前数字与主要阻塞见[状态快照](ACCEPTANCE_STATUS_3_2_0.md)，62 个 Android/Windows 编号状态见[验收矩阵](ACCEPTANCE_MATRIX_3_1_0.md)，完整用户可见案例见[客户端测试计划](FULL_CLIENT_TEST_PLAN_2026_08_28.md)，Issue 决策见[中央台账](ISSUE_TRIAGE_LEDGER_3_2_0.md)。旧的逐批时间线已移至[历史归档](ACCEPTANCE_HISTORY_3_2_0.md)。

## 一次只走一条最短证据链

1. **先判定是否仍是当前缺陷**：冻结 `HEAD`，对照报告版本、当前调用链、已有测试和已有审计。`already-fixed` 直接停止；证据不足记清再开条件；只有当前源码仍存在时进入修复。
2. **先做确定性复现**：找到首个错误状态，写最小红测或固定夹具。不要用反复 GUI 点击、任意延时、整库分析或重新构建代替定位。
3. **一次修完相邻所有权**：同时检查调用者、取消/退出、重复输入、迟到结果、持久化和资源释放，但不扩散到无关页面。
4. **集中验证**：改动稳定后跑受影响测试；Dart 编辑全部结束后只跑一次 analyze。只有正式候选才跑完整门禁和平台构建。
5. **批量做原生验收**：同一候选集中覆盖一组场景，失败项回源码修订；不为每个小改动单独构建、安装或启动 GUI。
6. **完成即同步**：通过相应门禁后提交并推送 `origin/master`，核对本地与远端 SHA；发布产物另走最终门禁。

## 执行批次

### 1. Issue 与源码审查

- 使用 [`docs/AGENT_WORKFLOW.md`](AGENT_WORKFLOW.md) 的 Rapid Issue lane。
- 当前开放 Issue 只在[中央台账](ISSUE_TRIAGE_LEDGER_3_2_0.md)维护分类、证据和再开条件。
- 不重复读取完整历史，不为没有代码变化的旧问题新增专项长文、构建或设备轮次。
- 功能请求先判断是否能作为现有链路的小增量；涉及新资源体系、外部数据源或跨平台迁移时进入独立设计批次。

### 2. UI、操作与数据

按同一页面族批量审查并测试：

- 首页：关注、热门、分区、搜索、卡片、分页、刷新和滚动保持。
- 设置与数据：主题、字号、播放器、弹幕、录制、代理、窗口、账号、标签、历史、WebDAV、IPTV/EPG、关于与更新。
- 交互共同合同：窄宽/短高、大字号、中英文、鼠标/触摸/键盘/系统返回、重复点击、路由退出、错误反馈、持久化和可访问名称。
- UI 修订只更新受影响的测试目录和完整案例目录；编号状态只在证据真正覆盖整行时变化。

### 3. 播放、弹幕与平台

对每个已注册平台统一检查：目录/搜索、房间身份、详情、画质、线路、请求头与 Cookie、播放、弹幕、下播/失效刷新、纯音频、多画面、全屏/PiP/后台和退出清理。国外平台在需要时使用本机 Clash 的既有代理配置；探针成功只证明对应 HTTP/协议边界，不替代客户端呈现。

新增平台按“公开入口或可维护接口 → 身份与分页 → 播放/录制解析 → 搜索/弹幕能力声明 → 配置迁移 → 确定性测试 → 双端候选”的顺序实施。没有稳定数据源的能力保持明确缺口，不以缓存或其他会话数据伪装实现。

### 4. 录制

同一候选集中覆盖：手动/自动开始、轮询、暂停/停止、短录/长录、HLS/FLV、续签与断流恢复、代理、后台、存储不足、缓存回收、合并、最终大小/时长、严格解码和进程/文件清理。状态机源码通过不等于媒体文件完整；最终文件必须由 `ffprobe`/严格解码和字节账本验证。

### 5. Android 原生批次

仅在网络 ADB 当前可见并且本轮需要原生证据时开始：

1. 通过仓库设备包装器取得共享设备租约；所有命令显式 `-s`。
2. 先核对型号、代号和系统；连接异常先查 `adb devices -l` 与 `adb mdns services`。
3. 只覆盖安装当前候选，安装前保存必要数据/元数据，结束后精确恢复测试夹具和系统状态。
4. 按矩阵 A0～A8 合并执行；同一候选避免反复安装和重复启动。
5. 保留“不重启手机/adbd、不切 Wi-Fi、不撤销授权、不改 ADB 端口、不更新 Root/LSP 模块、不随意 kill-server”的设备边界。

ADB 不在线时继续源码、测试和 Windows 工作，不把连接失败解释为配对丢失。

### 6. Windows 原生批次

先生成一次当前 x64 Release/便携候选，再复用同一实例完成 W0～W4：安装/启动、全部页面、100%/150%/200% DPI、主副屏、标题栏/托盘、播放/弹幕、全屏/PiP/多窗口、录制、CPU/GPU/内存/句柄/线程与退出回落。模型与任务成本规则只引用 [`AGENT_WORKFLOW.md`](AGENT_WORKFLOW.md#model-and-task-handoff)，本页不复制。

Issue #767 的物理性能对照必须在同一源、同一候选下比较 4K/150% 与 1440p/100%，记录实际纹理矩形、GPU 3D/Video Decode、CPU、工作集、单窗/双窗和退出回落；源码尺寸测试不替代该矩阵。

## 验证与构建门禁

- 文档/流程：链接、语法、相关静态检查与 `git diff --check`。
- 行为修订：受影响测试；Dart 改动稳定后一次 analyze。
- 候选批次：`tool/local_ci.ps1 -Scope Full`，随后按 [`BUILD_POLICY.md`](../BUILD_POLICY.md) 串行构建单一平台。
- Android：包名、版本、签名、ABI、16 KB、资源、哈希、覆盖安装和数据保留。
- Windows：Release EXE、便携 ZIP、安装器、运行库、独立目录启动、哈希和卸载/退出清理。
- 失败、取消或来源 SHA 不一致会阻断后续平台和发布；旧包证据只保留其历史边界。

## 3.2.0 发布门禁

以下条件全部满足后才进入发布：

1. 当前编号矩阵没有未处置的 P0/P1 `FAIL`；外部条件缺失有明确范围和证据。
2. 当前提交的完整质量门禁通过，工作树干净，本地与 `origin/master` SHA 一致。
3. Android 与 Windows 当前候选完成各自原生矩阵；发布范围内其他平台从同一提交串行构建并核验。
4. 所有安装包/压缩包/安装器绑定版本、提交、签名、SHA-256 和构建记录。
5. README、更新日志、已知限制、回滚说明与实际产物一致。
6. 发布后重新下载资产，独立核对哈希、内容和启动，再更新发布索引。
