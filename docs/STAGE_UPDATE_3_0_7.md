# v3.0.7 Android 竖屏真实画布与横屏入口修复

- 版本：`3.0.7+4095`
- 目标：Android `arm64-v8a` Release APK
- 上游：本轮保持冻结，只修复维护仓库竖屏回归
- 设备操作：代码审查、外部实现对照与自动化测试，不操作手机

## 根因

上一版已经把“编码画布、平台声明、有效内容、最终呈现”拆层，但仍有两个坐标契约错误：

1. 截图分析只返回归一化裁边，没有保存截图本身的宽高比；提交时又把裁边套到解码器报告的
   `aspectRatio`。抖音流的解码元数据、旋转或采样宽高异常时，这相当于把 A 坐标系的边界用到
   B 坐标系，节目比例会再次变窄。
2. 平台声明为竖屏、解码画布为横屏时，旧策略直接计算一组假想左右黑边；与此同时渲染器在
   没有实测裁边时又把原生纹理尺寸改成最终呈现比例。两次猜测叠加会横向拉伸或二次裁切。

竖屏普通页缺少横屏按钮是另一个独立布局问题：自适应页使用底部可拖动互动面板覆盖全画布，
播放器原有的底部全屏按钮位于面板下面，因此视觉和点击区域都被遮住。

## 修复设计

### 原子视觉证据

- `ActiveVideoContentObservation` 同时携带截图画布比例、归一化裁边和置信度；
- 两次画布比例与裁边都一致的观测才提交；暗场、转场和不一致结果继续保持当前几何；
- 提交后的有效节目比例始终由 `截图画布 × 截图裁边` 计算，不再混用解码尺寸；
- 新 URL、线路和清晰度继续开启新 geometry generation，旧观测不跨代复用。

### 呈现与纹理分离

- 平台宽高继续作为方向和异常元数据修正证据，但不生成裁剪坐标；
- `renderCanvasAspectRatio` 专门描述原生纹理画布，`effectiveAspectRatio` 专门描述可见节目；
- 原生纹理始终按真实画布比例放置，只有两次实测黑边才建立裁剪视口；
- 普通页、横屏全屏、系统 PiP 与应用内小窗共享有效节目比例，普通横屏源保持既有合同。

### 显式横屏全屏

- 竖屏普通页在互动面板上方显示独立“横屏全屏”按钮，面板三档高度变化时按钮同步移动；
- 点击后直接进入全屏并请求横屏，不依赖当前源方向；
- 该动作不修改“跟随直播源 / 跟随系统 / 始终横屏”的持久设置，退出后仍按用户偏好运行。

## `dtv_mobile` 对照结论

审查 `chen-zeong/dtv_mobile@15c254ac` 后，确认以下思想适合复用：

- 在同一次播放器回调中组合宽、高、旋转和像素宽高比；
- 只保留一个 fit/zoom 缩放所有者；
- 将自动旋转、手动全屏、手动退出和返回处理建模为显式状态；
- 播放器监听与实例按 URL 生命周期解绑和释放。

该仓库仅依据播放器 `VideoSize` 判断竖屏，没有平台声明与有效画面检测；其
`showFullscreen = isVideoAspectKnown && !isVerticalVideo` 还会直接隐藏竖屏视频的全屏按钮。
Pure Live 仅吸收上述架构思想，并独立实现视觉证据和始终可见的横屏入口。

## 回归

- 解码元数据异常但截图为直接 9:16 时，由两次全帧证据恢复正确比例；
- 解码元数据异常、截图为 16:9 画布内嵌 9:16 时，使用截图画布裁边且不拉伸；
- 平台竖屏提示与横屏画布冲突时不虚构黑边；
- 新 URL generation 清除上一画布裁边；
- 渲染层在没有实测裁边时保持原生画布比例；
- 竖屏互动面板上方始终存在可点击的横屏全屏入口；
- 普通横屏、旧布局、桌面分栏与 IPTV 视频专用布局不进入新分支。
