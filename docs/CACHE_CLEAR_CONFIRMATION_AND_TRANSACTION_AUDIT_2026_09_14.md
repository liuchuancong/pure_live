# 本地缓存清理确认与事务审计（2026-09-14）

## 范围与结论

本批复核“缓存与数据”页面从清理入口、确认路由到缓存控制器清理完成的完整事务。基线为 `56aacb16e5f732d69a880939341b26ef671072af`，实现提交为 `6bcbcb8b3051afb4a4d775376c45be29f98fe18e`。

旧页面仅在缓存控制器已经扫描、刷新图片或清理时禁用入口，确认弹窗打开期间仍视为闲置。同一清理行回调连续触发会叠加两个 `AlertDialog`；底层 `CacheController` 虽能合并真正的清理 Future，用户仍会看到重复确认路由。旧清理动作还是普通文本按钮，缺少明确的破坏性层级、纵向动作溢出策略和最小命中尺寸合同。

现由页面从创建确认路由前同步取得清理事务所有权，并在取消、系统返回、清理成功、部分失败或异常结束后统一释放。事务期间页面入口置灰，旧回调再次触发也会被同步门禁截断；用户确认后，门禁持续覆盖 `clearCache()` 的完整 Future，与底层清理合并共同形成 UI 和存储两层单次事务。

确认框使用根 Navigator、可滚动正文、16/20 窗口边距、420 px 正文宽度上限和向下动作溢出。取消与红色 Filled 清理动作均至少 48×48；320×480、3.0 倍英文文字下标题、说明和两个动作均保持可见并可命中。

## 交互合同

1. 清理入口从确认路由出现前到缓存清理 Future 结束始终只允许一个事务。
2. 快速重复触发只创建一个确认弹窗，也只提交一次底层清理。
3. 取消、点击遮罩或系统返回不清理数据，并立即恢复入口。
4. 清理进行期间入口保持禁用，旧回调也不能创建第二个确认路由。
5. 成功、部分失败和异常均走既有明确反馈，并在最后释放页面门禁。
6. 页面退出后不提交旧页面反馈，也不执行 `setState`。
