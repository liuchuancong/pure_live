# PureLive 数据存储架构规范

> Status: Proposed
> Scope: PureLive Flutter Monorepo
> Last Updated: 2026-10-12

## 1. 目标与设计原则

本文定义 PureLive 在 Android、iOS、Android TV、Windows、macOS、Linux 上的数据存储架构，统一存储边界、数据生命周期、错误处理与测试要求。

核心原则：

1. 先区分数据语义，再选择存储技术。
2. 业务模块依赖抽象接口，不直接依赖底层存储插件。
3. 持久化数据与可重建缓存必须分离。
4. Repository 负责业务数据访问与一致性，Storage Adapter 负责具体读写。
5. 文件和数据库操作默认异步，不阻塞 UI isolate。
6. 不允许将存储错误伪装成空数据或默认值。
7. 所有重要持久化结构都必须考虑版本迁移。
8. 存储接口应可测试、可替换、可诊断。
9. 不提前构建万能存储框架，按真实业务需求渐进扩展。
10. 外部插件不得默认拥有宿主应用的任意文件和数据库访问权限。

## 2. 数据分类

| 类别 | 典型数据 | 是否允许自动清理 |
|---|---|---|
| 业务持久化数据 | 收藏、播放列表、历史记录 | 否 |
| 应用设置 | 主题、语言、播放偏好 | 否 |
| 结构化业务数据 | 下载任务、元数据索引、源信息 | 否 |
| 可重建缓存 | API 响应、解析结果 | 是 |
| 图片缓存 | 封面、缩略图 | 是 |
| 用户文件 | 导入配置、脚本、M3U、备份 | 否，除非用户明确操作 |
| 下载媒体 | 视频、音频、本地媒体 | 按下载管理策略处理 |
| 临时文件 | 下载临时片段、导入临时文件 | 是 |
| 敏感凭据 | Token、Cookie、密钥 | 按安全策略清理 |
| 运行时状态 | 临时筛选、加载状态、未提交表单 | 通常可以 |

不能只根据文件扩展名判断数据类别。同样是 JSON，用户导入的配置和临时缓存拥有完全不同的生命周期。

## 3. 总体架构

推荐依赖关系：

```text
Feature / UI
    |
    v
Application Service / Use Case
    |
    v
Repository
    |
    +-----------------------+
    |                       |
    v                       v
Structured Storage      File Storage
    |                       |
    v                       v
Database Adapter        File System Adapter
```

可选能力：

- Preferences Store
- Secure Storage
- Cache Store
- Backup / Import / Export
- Plugin Storage Gateway

### 3.1 UI 层

UI 通过 Riverpod Provider、Application Service 或 Repository 访问数据。

禁止：

- Widget 直接执行 SQL。
- Widget 直接读写应用配置文件。
- Widget 直接拼接平台文件路径。
- Widget 直接依赖具体数据库驱动。
- 将数据库实体直接作为所有模块的公共模型。

UI 状态和持久化数据必须分离。只有明确需要跨进程重启恢复的数据才应持久化。

### 3.2 Application Service

负责组织跨 Repository 的业务流程，例如：

- 导入插件配置。
- 删除播放列表及其关联资源。
- 恢复备份。
- 更新数据并通知相关业务模块。
- 执行需要多个存储操作的业务用例。

Application Service 不应直接承担底层文件系统或数据库驱动的全部细节。

### 3.3 Repository

Repository 是业务数据访问边界，负责：

- 读取、保存、删除和查询业务数据。
- 组合本地数据库、远端 API 与插件数据。
- 处理业务查询条件、排序和分页。
- 决定缓存的使用时机和失效规则。
- 将底层异常转换为稳定的业务错误。
- 向上层提供必要的响应式数据流。

不要创建包含所有业务数据的万能 Repository，应按业务领域拆分。

### 3.4 Storage Adapter

Storage Adapter 负责：

- 底层数据库与文件 API。
- 连接生命周期。
- 事务执行。
- 序列化和反序列化。
- 数据库迁移。
- 平台差异封装。
- 基础存储错误转换。

它不应承担收藏规则、播放历史规则等领域逻辑。

## 4. 存储技术选型

### 4.1 结构化数据库

适用场景：

- 收藏、观看历史、播放列表。
- 下载任务与任务状态。
- 插件及数据源元数据。
- 需要筛选、排序、关联查询的数据。
- 需要分页和响应式查询的数据。
- 需要事务保证的数据。

建议优先评估 Drift + SQLite。

正式采用前，应验证目标平台支持、构建流程、迁移机制、并发行为及测试覆盖。

数据库规范：

1. Schema 必须版本化。
2. 每次 Schema 变更必须提供迁移。
3. 多步原子写入必须使用事务。
4. 分页查询必须有明确且稳定的排序。
5. 为高频查询字段建立合理索引。
6. 禁止 UI 直接拼接 SQL。
7. 数据库初始化和迁移必须有明确的生命周期所有者。
8. 迁移失败不得静默删除数据库并重建。
9. 大型查询和数据转换不能阻塞 UI。
10. 需要明确数据库损坏后的恢复策略。

### 4.2 键值存储

适用场景：

- 主题、语言、播放偏好。
- 少量、独立、无需复杂查询的配置项。

不适用场景：

- 大量业务记录。
- 复杂关联查询。
- 多条件筛选和排序。
- 需要多个字段原子更新的业务数据。

规范：

- 统一设置接口。
- 避免散落的魔法字符串。
- 明确默认值。
- 明确旧版本值的兼容策略。
- 明确设置删除和重置规则。
- 不存储 Token、Cookie 等敏感凭据。

### 4.3 安全存储

适用场景：

- 登录 Token。
- 刷新 Token。
- 敏感 Cookie。
- 加密密钥和其他认证凭据。

规范：

- 不将敏感凭据写入普通偏好设置。
- 不在日志、崩溃报告或普通备份中输出敏感值。
- 通过统一的 SecureStorage 抽象访问。
- 明确各平台安全存储的能力差异。
- 注销账户时按安全策略清理对应凭据。
- 不假设所有桌面平台提供完全相同的安全保证。

### 4.4 文件存储

适用场景：

- 用户导入的 TVBox 配置。
- M3U 播放列表。
- LX Music 脚本和其他插件文件。
- 用户导入的 JSON、YAML 等配置。
- 导出文件和备份。
- 下载媒体与大型二进制资源。

规范：

1. 所有路径通过统一路径服务获取。
2. 禁止业务模块硬编码平台目录。
3. 用户可见文件与应用私有文件采用不同目录策略。
4. 写文件优先采用临时文件加原子替换。
5. 导入前校验大小、格式、编码和内容。
6. 防止路径穿越与越权访问。
7. 明确文件删除后相关索引的处理方式。
8. 为异常中断产生的临时文件制定清理规则。
9. 不要把大型二进制资源全部存进数据库。
10. 不要把所有业务数据全部序列化成一个 JSON 文件。

### 4.5 缓存

缓存必须是可管理的独立能力。

每种缓存至少需要：

- 明确的 Cache Key。
- 明确的作用域。
- TTL 或其他失效规则。
- 容量限制。
- 清理策略。
- 并发读写规则。
- 失败后的回源或降级策略。

缓存不能成为唯一的数据来源，除非业务明确接受其数据丢失风险。

缓存 Key 不能总是只使用 URL。必要时应纳入用户身份、数据源 ID、配置版本、语言和其他影响结果的参数，避免串数据。

## 5. 推荐模块边界

以下为职责建议，不要求初期全部拆成独立 Package。

| 模块 | 职责 |
|---|---|
| storage_contracts | 基础存储接口、错误语义、通用约定 |
| storage_database | 数据库初始化、迁移、事务基础设施 |
| storage_preferences | 轻量设置读写 |
| storage_secure | 敏感凭据读写 |
| storage_files | 路径服务、文件读写与安全写入 |
| storage_cache | 缓存失效、容量与清理策略 |
| feature repositories | 业务数据访问和业务查询 |
| import_export | 配置导入、导出、备份与恢复 |
| plugin_storage_gateway | 插件存储权限和命名空间隔离 |

如果当前规模还不需要拆包，可以先创建一个 storage Package，内部使用清晰的目录划分。

只有在依赖边界、复用或独立测试确实需要时，再拆成多个 Package。

不要为了增加 Package 数量而制造无意义的抽象。

## 6. 数据所有权与模型边界

每类数据都必须有明确的所有者。

- 业务数据：负责业务规则、写入、删除、迁移和恢复。
- 缓存：负责过期、容量和清理。
- 文件：负责路径、元数据、生命周期和导入导出。
- 凭据：负责安全读写、访问权限和注销清理。
- 运行时状态：负责内存状态和是否需要恢复。

建议区分以下模型：

- Domain Model：业务语义。
- Persistence Model：数据库或持久化结构。
- DTO：网络或插件协议数据。
- UI State：界面展示状态。

小型模块不必机械地创建四套重复模型，但不同协议和生命周期之间应有明确的转换边界。

## 7. 读写与一致性规范

### 7.1 写入流程

推荐流程：

1. 校验输入和权限。
2. 转换为持久化模型。
3. 在事务或安全写入边界内提交。
4. 确认写入成功。
5. 更新或失效相关缓存。
6. 通知 Repository 或 Provider 刷新状态。

不能在实际写入失败后仍将 UI 标记为保存成功。

如果采用乐观更新，必须定义失败后的回滚或错误提示策略。

### 7.2 跨资源一致性

数据库事务不能自动覆盖文件系统和远端 API。

文件导入建议：

1. 写入临时文件。
2. 校验文件内容。
3. 原子替换目标文件。
4. 更新数据库索引。
5. 通知相关业务模块。

删除带文件的记录时，必须明确数据库记录和文件的删除顺序，并支持异常后的恢复或清理。

下载任务必须区分：

- 任务元数据。
- 临时下载文件。
- 最终媒体文件。
- 可重建的下载缓存。

多步骤操作失败时，应提供可重试或可补偿的恢复方案。

### 7.3 并发

规范：

- 对同一实体的并发写入定义冲突规则。
- 对同一文件的并发写入避免互相覆盖。
- 对重复请求可使用 single-flight 或幂等键。
- 不将 single-flight 视为数据库事务。
- 防止过期异步请求覆盖更新后的状态。
- 数据库并发写入采用明确的事务或队列策略。
- 大量 JSON 解码、文件扫描和数据转换不得阻塞 UI isolate。

## 8. 错误模型

至少区分：

- notFound：数据不存在。
- validation：输入或格式无效。
- permissionDenied：权限不足。
- unavailable：存储暂不可用。
- diskFull：磁盘空间不足。
- corrupted：数据损坏。
- migrationFailed：迁移失败。
- conflict：版本或并发冲突。
- cancelled：操作已取消。
- unknown：无法分类的错误。

底层异常可以作为 cause 保留，但不能直接把平台异常字符串当作稳定的业务 API。

禁止捕获所有异常后统一返回空列表或默认值。

需要区分“数据确实为空”和“数据读取失败”。

## 9. 初始化与迁移

建议启动顺序：

1. 初始化必要的平台绑定。
2. 初始化应用目录与路径服务。
3. 初始化安全存储。
4. 初始化数据库。
5. 执行必要迁移。
6. 初始化 Repository。
7. 创建依赖持久化数据的 Provider。
8. 启动需要存储环境的业务功能。

规范：

- 不要在每个页面重复初始化数据库。
- 迁移必须有版本记录。
- 迁移应具备明确的失败恢复策略。
- 迁移失败时不得静默删除用户数据。
- 需要兼容旧版本遗留的数据格式。
- 若允许应用降级，明确 Schema 不兼容时的处理方式。
- 对重要用户数据提供备份、导出或恢复方案。

## 10. 缓存清理策略

不能使用一个会删除所有数据目录的通用清理方法。

| 数据类别 | 清理策略 |
|---|---|
| 临时文件 | 操作完成后清理，启动时清理过期残留 |
| API 缓存 | TTL、容量限制、版本失效 |
| 解析缓存 | TTL、数据源版本变化时失效 |
| 图片缓存 | 独立容量限制与淘汰策略 |
| 下载媒体 | 由下载管理策略或用户操作清理 |
| 用户导入配置 | 默认保留，用户显式删除 |
| 收藏与历史 | 由业务操作或用户明确清除 |
| 凭据 | 根据注销、过期和安全策略清理 |

缓存清理必须只作用于明确属于缓存的数据，不得误删用户文件或持久化业务数据。

## 11. 导入、导出与备份

PureLive 需要兼容多种外部配置和脚本格式，因此导入系统应与存储底层分离。

推荐导入流程：

1. 读取文件或 URL。
2. 限制大小并验证编码。
3. 识别格式和版本。
4. 解析为临时 DTO。
5. 执行安全检查与语义校验。
6. 适用时显示导入预览。
7. 写入受管理的应用目录。
8. 更新数据库索引和来源元数据。
9. 通知相关 Provider 刷新。

备份应明确是否包含：

- 用户配置。
- 收藏、历史和播放列表。
- 插件配置与脚本。
- 下载任务元数据。
- 缓存。
- 登录凭据。

默认不导出 Token、Cookie 或密钥。

备份格式应带有版本号，恢复前校验完整性，并定义冲突处理策略。

## 12. 插件数据隔离

PureLive 可能接入 JavaScript、Python、M3U、TVBox 配置和 LX Music 脚本。

不得默认允许外部插件直接读写宿主数据库或任意访问文件系统。

建议：

- 插件通过受控的 Storage API 访问数据。
- 每个插件使用独立命名空间。
- 权限区分读取、写入、删除、网络访问和敏感数据访问。
- 宿主负责路径拼接和规范化。
- 拒绝路径穿越与越权访问。
- 插件卸载时明确保留、导出或删除数据。
- 插件升级时采用版本化配置迁移策略。
- 插件运行时不直接获得宿主数据库连接。
- 对插件数据设置必要的容量和资源限制。

插件隔离是安全边界，不能仅依赖目录命名。

## 13. Riverpod 集成

存储基础设施应尽量保持为普通 Dart 服务，不强制依赖 Riverpod。

规范：

- 在应用组合根创建数据库、存储服务和 Repository。
- 通过 Provider 注入依赖，支持测试替换。
- Notifier 或 AsyncNotifier 负责状态编排，不代替 Repository。
- Provider dispose 不得意外删除持久化数据。
- 数据库 watch stream 可用于响应式 UI。
- 响应式订阅必须管理生命周期。
- 只持久化确实需要跨重启恢复的数据。
- 不要默认将整个 Provider State 自动序列化。

## 14. 与分页模块的边界

分页模块只负责逻辑分页状态、加载协调和分页结果，不负责决定数据如何持久化。

- Repository 决定数据来源。
- 数据库负责本地查询、排序和分页。
- 文件索引通过 Repository 查询。
- 缓存可以缓存分页结果，但必须定义 Key 和失效策略。
- Pagination Controller 不直接依赖 Drift、文件 API 或 HTTP Client。
- 本地响应式数据由 Repository 或数据库监听变化，再更新分页状态。

## 15. 测试要求

### 单元测试

- 序列化与反序列化。
- 默认值和旧格式兼容。
- Repository 查询、排序、过滤和分页边界。
- 缓存 TTL、失效与容量限制。
- 错误映射。
- 路径规范化与路径穿越防护。
- 并发请求与过期结果处理。

### 集成测试

- 数据库初始化与迁移。
- 事务提交和回滚。
- 文件原子写入与异常中断恢复。
- 导入、导出、备份和恢复。
- 删除记录与孤儿文件清理。
- 并发读写。
- 注销后的敏感数据清理。
- Schema 升级与旧数据兼容。

### 跨平台验证

- Android。
- iOS。
- Android TV。
- Windows。
- macOS。
- Linux。

平台差异应尽可能由适配器层测试，不应让业务层测试依赖真实设备目录或真实密钥链。

## 16. 日志与诊断

允许记录：

- 操作类型。
- 操作耗时。
- 迁移版本。
- 影响的数据条数。
- 缓存命中情况。
- 错误类别。
- 可安全公开的诊断信息。

禁止记录：

- Token。
- Cookie。
- 密码。
- 私钥。
- 完整敏感配置。
- 不必要的个人目录信息。

高频缓存日志应使用适当的日志级别或采样，避免日志过量。

## 17. 推荐实施顺序

### Phase 1：确定边界

- 建立数据分类清单。
- 为每类数据指定 Owner。
- 明确持久化方式和清理规则。
- 统一错误语义。
- 统一应用目录访问入口。

### Phase 2：建立最小基础设施

- PathProvider / 应用目录服务。
- FileStorage 基础接口。
- PreferencesStore。
- Database 初始化、迁移与测试。
- 有实际需求时加入 SecureStorage。

### Phase 3：接入真实业务

优先选择设置、收藏或播放历史等真实业务验证：

- Repository 边界。
- 数据迁移。
- 查询性能。
- 错误处理。
- 响应式更新。
- 测试可替换性。

### Phase 4：增加缓存和导入导出

按真实性能和产品需求增加：

- 缓存策略。
- 配置导入导出。
- 备份恢复。
- 清理工具。

不要过早建设复杂的通用缓存框架。

### Phase 5：接入插件存储

外部运行时落地后，再完善：

- 插件命名空间。
- 存储权限。
- 容量限制。
- 卸载清理。
- 配置迁移。
- 安全审计。

## 18. 明确禁止的做法

- Widget 直接访问数据库或文件系统。
- 业务模块硬编码平台路径。
- 用户数据与缓存使用相同的清理策略。
- 将所有异常统一转换为空列表。
- Schema 变更没有迁移。
- Token 或 Cookie 写入普通设置或日志。
- 插件直接访问宿主数据库。
- 将所有数据放进一个 JSON 文件。
- 将所有数据都放进数据库，包括大型媒体和临时文件。
- 为了抽象而提前构建多层泛型存储框架。
- 未经验证就声称某个存储插件在所有平台具有完全一致的安全能力。
- 删除用户数据前不验证数据所有权和生命周期。

## 19. 新增数据类型的验收清单

每一种新数据进入系统前，必须回答：

- [ ] 谁拥有这份数据？
- [ ] 它是持久化数据、缓存、文件还是运行时状态？
- [ ] 数据丢失是否可接受？
- [ ] 需要事务、排序、过滤、分页或响应式监听吗？
- [ ] 是否包含敏感信息？
- [ ] 是否需要加密或安全存储？
- [ ] 何时过期、清理、删除或迁移？
- [ ] 写入失败后如何处理？
- [ ] 如何处理并发写入和过期请求？
- [ ] 是否需要导入、导出、备份或恢复？
- [ ] 是否需要插件权限隔离？
- [ ] 如何进行单元测试、集成测试和跨平台测试？

## 20. 最终建议

PureLive 不需要一开始就实现一个万能数据存储平台。

建议先建立：

1. 统一的应用目录与路径服务。
2. 一个结构化数据库基础设施，例如经过验证后采用 Drift + SQLite。
3. 一个轻量设置接口。
4. 一个安全凭据接口。
5. 一个文件存储接口。
6. 明确区分持久化数据与可清理缓存。
7. 按业务领域划分 Repository。
8. 统一的迁移、错误处理和测试规范。

底层存储可以统一接入，但数据语义、生命周期和所有权不能混为一谈。

## 附：推荐的 Pub 包与使用边界

可靠性分级：

- 普通偏好设置：主题、语言等可以容忍重新设置的数据。
- 重要设置：默认播放器、播放行为、用户自定义配置等，写入成功后才确认完成。
- 关键业务数据：收藏、播放列表、历史记录等，使用 SQLite 事务，必要时配合备份。

| 用途 | 推荐包 | 优先级 | 说明 |
|---|---|---|---|
| 结构化数据库 | drift | 必须（结构化数据） | SQLite、类型安全查询、事务、响应式查询 |
| Flutter 数据库连接 | drift_flutter | 推荐 | 简化 Flutter 多平台数据库初始化 |
| 数据库代码生成 | drift_dev | 开发依赖 | 生成表和查询相关代码 |
| Dart 代码生成 | build_runner | 开发依赖 | 执行 Drift 代码生成 |
| 安全凭据 | flutter_secure_storage | 推荐 | Token、敏感 Cookie 等；需核对各平台支持及最低系统版本 |
| 应用目录 | path_provider | 推荐 | 获取应用文档、支持文件和临时目录 |
| 路径处理 | path | 推荐 | 跨平台路径拼接与规范化 |
| 文件操作 | file | 可选 | 需要统一文件操作接口时使用 |
| 文件选择 | file_selector | 推荐 | 用户导入、导出配置文件 |
| 跨平台文件数据 | cross_file | 按需 | 统一处理文件对象和字节数据 |
| 备份压缩 | archive | 按需 | ZIP 备份、导入包 |
| 内容校验 | crypto | 按需 | SHA-256 等完整性校验 |

缓存场景建议：

- 图片、封面、远端文件缓存：可评估 flutter_cache_manager。
- API JSON 响应缓存：先基于现有网络层封装自己的缓存接口。
- 插件解析结果缓存：先实现轻量缓存抽象，按需选择内存或磁盘后端。
- 大型媒体下载：交给下载模块和文件存储模块管理。
- 收藏、历史、播放列表：使用 Drift，不使用临时缓存替代。

drift_flutter 已提供 Flutter 环境下的数据库连接集成，优先按它的当前文档配置原生 SQLite 依赖，不要未经验证就重复添加底层 SQLite 库。
