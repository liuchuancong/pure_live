# Issue #869 Android 进入直播间覆盖系统音量审计（2026-09-19）

## 结论

上游 Issue [#869](https://github.com/liuchuancong/pure_live/issues/869) 报告：Android 在某直播间把软件音量调到 0、退出后于系统或其他直播间重新调高媒体音量，再进入原房间时，系统媒体音量会被强制恢复为 0；报告称 3.1.4 每次可复现。当前源码能够确定性复现：移动端 `VideoController._initVolumeController` 读取设备当前媒体音量后，只要设备并非已经静音，就把房间持久值通过 `VolumeController.setVolume` 写回共享系统媒体流。

冻结的 `upstream-v3.1.2` 与 `v3.1.4` 源码都包含同一“当前设备值大于 0 → 写入房间保存值”路径，因此报告中的“3.1.2 最后正常”没有得到源码历史支持，可能还涉及当时插件、设备或操作时序差异；这不影响 3.1.4 与修复前当前源码的根因成立。

提交 `789f03ccf62ecaa1cf810df311d80c149eed02a2` 调整移动端初始化所有权：普通进入直播间只采纳设备当前媒体音量来更新应用显示，不再把过期的单房间快照写回系统，也不擦除桌面/多画面的房间偏好；“全局静音”是用户明确选择的全应用动作，仍是进入时可写 0 的唯一偏好例外。该项分类为 `implemented-in-current-source / android-native-candidate-recheck-pending`。

## 修复后的合同

1. Android/iOS 普通进入直播间时，系统媒体音量是权威当前值；房间历史值不得覆盖它。
2. 设备音量为 0 或非 0 都只更新当前直播界面，不触发初始化写入，也不擦除桌面/多画面仍在使用的房间偏好。
3. 用户在当前直播间主动调节音量时，原有系统写入、原生量化回报、界面更新和持久记录保持。
4. 初始化读取期间若收到更新的原生音量事件，事件继续以修订代次胜出；旧房间、已退出控制器和超时读取不得产生迟到写入。
5. 明确启用“全局静音”时仍将当前媒体流设为 0；关闭全局静音后，下次普通进入继续以设备当前值为准。
6. 桌面播放器的房间独立音量、多画面每格音量、音量弹窗事务和物理按键媒体流路由不随本次修订改变。
