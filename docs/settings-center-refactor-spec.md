# PureLive v4 设置中心智能拆分与自动重构规范

## 1. 文档目标

建立一套适用于编码代理的设置中心重构规范，使编码代理能够自主完成以下工作：

1. 理解现有设置中心的完整结构与功能。
2. 分析每项设置的真实用途、依赖关系和所属业务。
3. 判断哪些内容应该保留在一起，哪些内容应该拆分。
4. 自主设计合理的分类、子页面和页面层级。
5. 识别重复配置、职责混乱、过度耦合和不合理的设置归属。
6. 制定迁移方案并执行重构。
7. 验证重构没有破坏现有功能。
8. 在后续开发中持续遵守同一套规范。

本规范不预先指定最终分类数量、页面名称、文件数量或目录结构。

最终结构必须根据实际项目分析得出，而不是套用预设模板。

## 2. 核心原则：先理解，再决策

不得在未完成代码审计前直接拆分设置页面。

必须先理解现有实现，再确定拆分方案。

分析范围包括：

- 设置入口和设置页面。
- 所有设置项及其说明。
- 设置模型、状态管理和持久化。
- 设置项之间的依赖关系。
- 设置对业务模块的影响。
- 设置与平台能力的关联。
- 设置的默认值、有效范围和副作用。
- 设置项之间的重复、冲突和共享关系。
- 设置页面与其他业务页面之间的交互。
- 已有的配置迁移、恢复默认和导入导出机制。

不能仅凭页面标题、变量名称或所在文件夹判断设置的归属。

必须追踪实际调用关系，必要时检查设置从 UI 到业务执行再到持久化的完整链路。

## 3. 设置项分析模型

应以单个设置项为基本分析单位，而不是以现有页面或文件为基本单位。

对每项设置，分析以下维度：

### 3.1 功能语义

- 该设置解决什么问题？
- 用户在什么场景下会修改它？
- 修改后实际影响什么行为？
- 它属于通用应用能力还是特定业务能力？

### 3.2 业务归属

判断设置与哪些功能存在直接关系。

如果一个设置只服务于某个业务，不应仅因为它与其他设置使用相同技术实现，就被放入通用设置。

如果一个设置被多个业务共同使用，也不应因为最初由某个业务引入，就永久归属于该业务。

### 3.3 关联与依赖

识别：

- 哪些设置必须共同理解或调整。
- 哪些设置之间存在前置条件。
- 哪些设置仅在特定条件下有效。
- 哪些设置虽然相关，但用户通常需要分别调整。
- 哪些设置实际上是同一个配置的重复入口。

### 3.4 使用频率与复杂程度

根据实际产品行为判断：

- 是否属于常用配置。
- 是否属于低频高级配置。
- 是否涉及复杂参数。
- 是否需要独立的交互流程。
- 是否具有较高的误操作风险。

如果缺乏使用频率数据，不得伪造用户行为结论，应根据功能复杂度和任务完整性作出判断，并标记不确定性。

### 3.5 平台适用性

识别设置适用的平台和输入方式。

区分：
- 所有平台通用的配置。
- 仅部分平台支持的配置。
- 具有不同平台实现、但语义相同的配置。
- 仅某一平台存在的专属功能。

不得因为某项设置只在一个平台生效，就自动认定它必须独立成页。

## 4. 自主决定拆分结构的规则

应根据分析结果确定页面边界，不使用固定数量阈值作为唯一标准。

### 4.1 应当考虑合并的情况

出现以下情况时，应评估是否合并：

- 多个页面实际上服务于同一个用户任务。
- 页面内容过少，独立存在没有明显价值。
- 用户必须频繁跨页面调整一组紧密相关的选项。
- 多个页面具有重复的说明、操作或配置入口。
- 拆分只是由原有代码文件边界造成，并不符合用户的理解方式。

合并前必须确认设置的业务语义和依赖关系一致，不能为了减少页面数量而混合无关功能。

### 4.2 应当考虑拆分的情况

出现以下情况时，应评估是否拆分：

- 一个页面包含多个彼此独立的用户任务。
- 不同设置群组的业务目标明显不同。
- 页面内容过于密集，难以扫描和定位。
- 高级参数明显干扰常用设置。
- 不同内容需要不同的交互流程或验证机制。
- 页面包含多个可独立管理的复杂对象或工作流程。
- 不同内容具有不同的业务生命周期或维护边界。

### 4.3 不允许的拆分方式

禁止：

- 按照固定设置项数量机械拆页。
- 按照原有 Dart 文件逐个复制。
- 为每个开关创建独立页面。
- 仅因为使用不同的 Provider 或 Repository 就拆成不同分类。
- 把所有无法归类的设置集中到一个杂项页面。
- 以技术实现细节代替用户可以理解的分类。
- 为尚不存在的功能提前创建大量空页面。

### 4.4 分类不明确时的处理

当某项设置可能属于多个领域时，编码代理应检查它的主要用户任务、实际影响范围和依赖关系。

如果仍然存在多种合理方案，应列出候选归属及其利弊，选择最符合现有架构与用户使用场景的方案。

对于影响重大、无法从代码确定的产品决策，不得自行删除或改变原有语义，应保留行为并明确记录待确认事项。

## 5. 结构设计要求

完成分析后，编码代理自主设计适合当前项目的设置中心结构。

结构应满足：

- 分类能够被普通用户理解。
- 同一层级的分类具有一致的抽象粒度。
- 页面职责明确，避免内容重复。
- 设置项有且只有一个规范的配置定义。
- 页面层级尽可能浅。
- 高级功能不会妨碍常用操作。
- 平台差异能够被清晰表达。
- 业务模块可以在不破坏现有设置中心的前提下扩展。
- 结构与现有项目的架构约定一致。

必须先产出实际的设置清单、分类建议和拆分理由，再开始大规模迁移。

不得因为本规范没有规定具体分类，就自行认为必须采用任何固定分类方案。

## 6. 架构与职责边界

重构过程中必须区分以下职责：

### 展示层

负责设置页面布局、分组、控件、说明、搜索结果和页面导航。

不得将复杂的持久化、业务执行或配置迁移逻辑直接堆积在页面组件中。

### 状态与应用逻辑层

负责设置状态读取、变更流程、依赖处理、恢复默认及相关应用操作。

遵循项目现有的 Riverpod 3 使用方式，避免创建新的全局单例或重复的状态源。

### 配置模型与业务规则

负责设置的语义、类型、默认值、有效范围、约束和必要的校验。

同一配置不应在不同页面维护互相独立的定义。

### 持久化层

负责配置的存储、读取、迁移和必要的数据兼容。

页面拆分不得擅自更换现有存储方案，也不得破坏已有用户配置。

以上是职责约束，不是强制创建固定数量的文件或目录。应根据实际代码决定合适的组织方式。

## 7. 设置项与设置页面必须解耦

设置项的存在不应依赖某个页面文件。

应评估如何使设置的定义、配置状态和页面展示保持合理的独立性。

要求：

- 页面调整不应导致配置身份发生变化。
- 配置应具有稳定且明确的语义。
- 同一个配置不应因在多个页面出现而产生多个独立存储值。
- 如果同一设置确实需要在多个位置提供快捷入口，应共享同一个配置定义和状态。
- 任何配置归属变化，都不应自动触发配置数据重置。
- 不得为实现页面拆分而引入不必要的抽象框架。

## 8. 自动重构执行流程

### 阶段 A：完整审计

扫描设置入口、页面、设置项、状态、存储、业务调用和平台条件。

输出：
- 现有设置结构。
- 设置项清单。
- 配置依赖关系。
- 重复和冲突问题。
- 页面过载和职责混乱问题。
- 现有实现中无法确认的事项。

本阶段不得修改业务代码。

### 阶段 B：形成拆分方案

根据审计结果自行确定：

- 最终分类。
- 每个分类的职责。
- 页面与子页面边界。
- 设置项迁移目标。
- 应合并、拆分或保留的现有页面。
- 需要保留的兼容行为。
- 迁移风险和验证方法。

每项重要结构调整都必须给出理由，不能只提供一份新的菜单列表。

### 阶段 C：检查方案一致性

开始重构前，检查：

- 是否存在职责重复的分类。
- 是否出现过深的页面层级。
- 是否把无关配置放在同一页面。
- 是否拆分过度。
- 是否遗漏现有设置项。
- 是否错误地改变了配置语义。
- 是否需要调整平台可见性。
- 是否会影响既有配置数据。

发现问题后先修订方案。

### 阶段 D：实施迁移

按照风险从低到高执行：

1. 整理设置项的归属与稳定身份。
2. 拆分或合并页面。
3. 迁移状态读取和交互逻辑。
4. 调整导航与搜索。
5. 处理平台适用性。
6. 清理已经确认不再使用的旧实现。

禁止一次性删除大量旧代码后再尝试恢复功能。

对于涉及配置迁移、存储格式或公共 API 的修改，应单独评估兼容性和回滚方案。

### 阶段 E：自动验收

实际运行适用于项目的检查，至少覆盖：

- 设置项完整性。
- 配置 ID 或键的唯一性。
- 默认值与数据持久化。
- 设置修改后的真实业务效果。
- 页面入口与导航有效性。
- 搜索结果的准确性。
- 平台显示条件。
- 恢复默认与配置导入导出。
- 现有用户数据兼容性。
- 静态分析、相关测试及必要的平台构建。

不能仅凭代码能够编译，就判定重构成功。

### 阶段 F：总结并持续维护

交付实际修改结果、测试结果、未解决问题和后续建议。

将稳定的分类规则、决策原则和验收标准保留为项目级文档，让后续编码任务能够读取和遵循。

不应把某次重构产生的具体分类永久固化成不可更改的模板。

## 9. 自动化决策权限

编码代理可以自主决定：

- 分类和子页面的数量。
- 页面拆分与合并方案。
- 设置项在页面之间的迁移。
- 符合现有架构约定的代码组织方式。
- 重复 UI 的清理。
- 必要的导航、搜索与测试调整。

编码代理不得未经依据擅自决定：

- 删除现有功能。
- 更改设置的默认行为。
- 重置或丢弃用户配置。
- 改变配置的业务含义。
- 引入与现有架构冲突的新框架。
- 在缺乏依据时改变跨平台行为。
- 将不确定的产品决策伪装成已确认的需求。

对于存在重大风险或无法从源码推断的决策，应尽可能保留原有行为，并将具体问题提交确认。

## 10. 最终完成标准

只有满足以下条件，才算完成：

1. 已经分析整个现有设置中心，而非只分析入口页面。
2. 最终结构由实际代码和用户任务推导而来。
3. 每项现有设置都有明确的处理结果。
4. 每项重要拆分和合并均有合理依据。
5. 页面、状态和持久化之间的职责清晰，页面不应太长，过多可增加二级甚至三级四级路由，需要兼容移动端显示。
6. 没有无故丢失功能或破坏用户配置。
7. 常用设置易于定位，高级设置不会造成不必要的干扰。
8. 相关测试和检查已实际执行，并报告真实结果。
9. 后续新增设置时，编码代理可以依据同一套规则继续判断如何组织，而不必重新设计整套规范。
10. 不写测试，不build运行。

**最终原则：本规范约束编码代理如何分析、如何决策、如何实施和如何验证，不预先替编码代理决定设置中心必须长什么样。**
