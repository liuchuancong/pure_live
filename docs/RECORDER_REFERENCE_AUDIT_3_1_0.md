# v3.1.0 直播录制参考项目审计

审计日期：2026-08-31。参考基线固定为：

- [`biliup/biliup@c4dbf81c5d3d`](https://github.com/biliup/biliup/commit/c4dbf81c5d3dbae7036660ddc180f10eb183d102)（MIT）；
- [`bililive-go/bililive-go@37d1d0e7d7a1`](https://github.com/bililive-go/bililive-go/commit/37d1d0e7d7a18ef31d592f8bdb17089518d12900)（GPL-3.0）。

本审计提取可验证的状态机、故障边界和验收方法，不直接搬运不同许可证项目的实现。Pure Live 的播放器、平台适配器与移动端录制仍保留自己的 Dart/Flutter 架构。

## 1. 已采用或已经具备

| 参考能力 | Pure Live 当前设计 | v3.1.0 动作 |

## 2. 本轮新增的协议韧性

`biliup` 当前基线修复了 Bilibili 畸形弹幕包导致解码任务终止的问题。对 Pure Live 的独立审计发现：既有解析器已经检查 16 字节包头、包长、剩余长度并捕获顶层异常，连接不会因为一次 Dart 解码异常直接退出；但压缩输出大小和单消息包数量仍缺少硬上限。

v3.1.0 因此补齐：

1. WebSocket 单消息编码大小上限；
2. 单消息内最大协议包数量；
3. zlib/Brotli 流式解压输出上限，避免高压缩比输入一次性展开为不受控列表；
4. 压缩包递归深度上限；
5. 零长度包、合法包后畸形包、过深压缩包之后连接继续解析的回归测试。

这些限制只丢弃当前不可信 WebSocket 消息；后续消息仍由同一连接处理，既有已解析弹幕也不会回滚。

## 3. 录制状态机采用边界

Pure Live 面向交互式播放器，不能照搬服务器录播器“无限重试”的默认值。移动端和桌面端统一采用以下边界：

- **准备中**：解析房间、画质和首条可打开输入；未写入文件前不显示伪造的 `0 B / 0M` 录制速度；
- **录制中**：文件大小、时长和速率只从真实输出文件采样，跨重连保持累计值单调；
- **短暂失败**：指数退避并刷新当前平台租约；同画质当前线路续签优先，随后才轮换线路/画质；
- **确定下播**：停止调度，不把平台网络错误误判为下播；
- **用户停止**：立即取消解析、续签和重连，等待 FFmpeg 收尾并释放文件句柄；
- **不可恢复失败**：保留最后错误类别、平台、画质、线路和脱敏诊断，禁止只显示“录制失败”。

## 4. 暂不并入稳定批次的平台

参考项目还覆盖 AcFun、OPENREC、微博、YouTube、TikTok 等站点。新增一个首页入口并不等于完整平台支持；至少需要目录/搜索、房间状态、画质/线路、播放租约、弹幕、观看指标、录制和登录边界八项合同。v3.1.0 先把现有十个平台的播放与录制矩阵做实，不在稳定版冻结阶段加入只有单一解析入口的平台。

后续候选按以下顺序评估：公开入口与区域可达性 → 登录依赖 → URL 寿命和 CDN → 弹幕协议 → 指标语义 → 录制合法收尾 → Android/Windows 实机。每个平台都需要独立探针和故障夹具后再进入默认导航。

## 5. 发布验收

- 参考项目的“支持平台”列表不作为 Pure Live 已支持证据；
- 接口探针通过不等于播放器/录制通过；
- 30 秒短录通过不等于短签名长时续接通过；
- 单元测试通过不等于 Android 后台、Windows DPI/任务栏和真实磁盘路径通过；
- v3.1.0 Release 只写入本轮取得证据的结论，未执行项继续保留在 `ACCEPTANCE_MATRIX_3_1_0.md`。
