
# PureLive 分页核心技术设计规范

- 文档状态：提案
- 所属模块：`pagination_core`
- 支持平台：Android、iOS、Android TV、Windows、macOS、Linux
- 状态管理：Riverpod 3.x
- 数据模型：不可变状态，按需使用 Freezed

## 1. 设计目标

### 1.1 核心原则

分页核心是一个独立于平台、界面和数据来源的分页引擎。

它只负责分页状态、分页计算和分页操作，不负责获取数据，也不负责组装数据。

分页核心负责：

- 当前页码与每页条数。
- 已知总条数与总页数计算。
- 当前界面需要展示的数据。
- 页码导航。
- 数据替换与追加。
- 刷新流程协调。
- 加载状态与错误状态。
- 并发请求保护。
- 过期请求结果保护。
- 失败重试。
- 支持稳定标识的数据项更新。
- 生命周期与资源释放。

以下职责属于外部应用逻辑：

- HTTP 请求。
- Repository 数据访问。
- 服务端页码转换。
- 服务端批次聚合。
- 数据去重。
- 缓存管理。
- 服务端全量数据加载。
- 本地数据切片。
- 数据过滤与排序。
- 业务特定的刷新操作。
- 直播间状态同步。
- 数据库订阅。

### 1.2 核心架构约束

分页核心不得关心数据来自哪里，也不得关心数据是如何组装的。

外部数据加载器接收逻辑分页请求，返回已经准备好的分页结果。

返回的数据必须对应请求的逻辑页。分页核心不得为了填满页面而自行追加网络请求。

例如，前端每页需要 100 条数据，而服务端每次最多返回 20 条，则外部数据加载器负责请求并合并多批数据，直到满足逻辑页要求或确认数据已经结束。

### 1.3 非目标

分页核心不负责：

- 替代网络请求库。
- 实现 Repository。
- 编写服务端 API 客户端。
- 自动推断服务端分页规则。
- 执行数据库查询。
- 实现虚拟列表渲染引擎。
- 依赖 Flutter Widget。
- 依赖 `paging_view`。
- 包含应用特定的业务规则。

## 2. 模块职责划分

### 2.1 分页核心

分页核心包含：

- 分页数据模型。
- 分页状态。
- 分页控制器。
- 分页计算工具。
- 页码导航策略。
- 刷新策略。
- 请求生命周期管理。
- 通用分页操作。

核心层应避免直接依赖 `BuildContext`、`ScrollController`、Widget、本地化、网络客户端或业务 Repository。

### 2.2 分页界面适配层

界面适配层负责将用户交互转换为分页控制器操作。

手机端适配层：

- 下拉刷新。
- 无限滚动。
- 加载更多指示器。
- 列表结束提示。
- 加载失败后的重试入口。

桌面端适配层：

- 数字页码导航。
- 上一页与下一页。
- 首页与末页。
- 直接跳转指定页。
- 当前页和总页数展示。

界面适配层不得自行实现网络分页循环或重复实现分页计算逻辑。

### 2.3 外部数据加载器

外部数据加载器负责为指定逻辑页准备数据。

它可以由 Repository、应用服务、本地数据适配器或其他业务层组件实现。

其职责包括：

- 获取所需数据。
- 将逻辑页转换为服务端请求。
- 合并多个服务端响应。
- 执行缓存策略。
- 执行过滤和排序。
- 返回准确的总条数或后续数据状态。
- 按约定处理外部请求失败。

### 2.4 Repository 与网络层

Repository 负责业务数据访问。

网络请求必须经过 PureLive 已有的网络封装，例如 `live_net`，而不是在分页核心中实现。

分页核心不得直接依赖 `live_net`。

## 3. 统一分页数据契约

### 3.1 分页请求

逻辑分页请求包含：

- `page`：从 1 开始的逻辑页码。
- `pageSize`：前端期望的每页条数。

逻辑页码与上游 API 的页码、偏移量和批次大小相互独立。

示例：

```dart
const request = PaginationRequest(
  page: 3,
  pageSize: 100,
);
```

表示前端需要第 3 个逻辑页，期望最多返回 100 条数据。

它不代表上游服务端必须接收 `page=3&pageSize=100`。

### 3.2 分页结果

成功结果包含：

- `items`：已经准备好的当前逻辑页数据。
- `totalCount`：符合当前查询条件的总条数，未知时为空。
- `hasMore`：是否还有后续逻辑页，未知时为空。

加载器必须保证返回的数据对应请求的逻辑页。

当数据已经结束时，最后一页可以少于 `pageSize` 条；空数据也是合法结果。

如果数据源使用变长批次，不能仅凭某次响应条数不足就认定数据已经结束。外部加载器必须负责判断后续数据是否仍然存在。

### 3.3 总条数未知的情况

某些服务端 API 不提供总条数。

此时：

- `totalCount` 保持未知。
- 如果可以判断是否还有后续数据，则提供 `hasMore`。
- 控制器不得自行编造总页数。
- 界面不得显示具有误导性的总页数。
- 如果加载器无法定位任意页，则不应假设可以直接跳转任意页。

当总条数已知时，以总条数作为页码边界判断依据。

当总条数未知时，控制器依赖 `hasMore` 及加载器约定的后续数据判断方式。

## 4. 数据来源接入规范

分页核心不定义数据来源模式枚举。

所有数据源都实现相同的逻辑分页契约，内部实现可以完全不同。

### 4.1 服务端页码分页

服务端直接支持页码和每页条数参数。

加载器将逻辑分页请求转换为服务端请求，解析响应后返回统一分页结果。

例如：

- 逻辑页码：3。
- 逻辑每页条数：20。
- 服务端请求：第 3 页，每页 20 条。
- 返回结果：逻辑第 3 页的数据。

如果服务端使用从 0 开始的页码、游标、偏移量或其他字段名称，只需由加载器负责转换。

### 4.2 服务端固定或变长批次分页

服务端返回的批次数量可能小于、等于或大于预期值。

外部加载器负责组装前端需要的逻辑页。

例如：

- 前端每页需要 100 条。
- 服务端每次最多返回 20 条。
- 数据充足且每批均返回 20 条时，需要请求 5 次。

加载器必须正确处理：

- 服务端单次返回数量限制。
- 短批次。
- 空批次。
- 重复数据。
- 不同批次之间的数据重叠。
- 后续游标。
- 部分请求失败。
- 请求取消。
- 数据源结束条件。

收集到足够的逻辑页数据，或者确认数据源已经结束后，加载器应停止继续请求。

不得假设每次服务端响应都包含请求的全部条数。

如果聚合过程中的某次请求失败，加载器必须遵循明确的失败策略，不得将未完成的聚合结果静默地当作完整成功结果返回。

### 4.3 服务端返回全量数据

加载器可以一次获取完整数据集并缓存。

后续逻辑分页请求直接从缓存数据中切片并返回结果。

对于完整数据集 `D`、页码 `p` 和每页条数 `s`：

```text
start = (p - 1) * s
end   = min(start + s, D.length)
```

实际实现必须安全处理越界页码和空数据集。

当数据集发生变化时，加载器负责刷新数据快照，并基于更新后的数据重新计算目标页。

分页核心不需要知道这些数据来自一次全量请求。

### 4.4 本地响应式数据

加载器可以从内存集合、数据库、状态提供器或响应式数据源读取数据。

它负责获取一致的数据快照，并返回指定逻辑页的数据。

数据发生变化时：

1. 应用更新或失效处理底层数据快照。
2. 应用触发分页刷新，或者通过明确支持的数据更新接口提交变化。
3. 控制器重新计算页码边界。
4. 界面接收更新后的分页状态。

如果数据源具有响应式订阅能力，订阅的生命周期属于外部适配器。适配器释放时必须取消不再需要的订阅。

### 4.5 其他数据来源

统一契约还应支持：

- 游标分页 API。
- 搜索结果。
- 筛选后的数据集合。
- 数据库查询。
- 多数据源合并。
- 插件提供的数据。
- 缓存与网络混合数据。
- 排序和分组数据。

只要新数据源能够满足逻辑分页契约，就不应要求修改分页核心。

## 5. 分页状态设计

分页状态应为不可变对象，至少包含：

- `items`：当前分页界面展示的数据。
- `currentPage`：当前逻辑页码。
- `pageSize`：逻辑每页条数。
- `totalCount`：已知总条数，未知时为空。
- `hasMore`：后续数据状态，未知时为空。
- `isInitializing`：是否正在首次加载。
- `isRefreshing`：是否正在刷新。
- `isLoadingMore`：是否正在加载下一页。
- `isChangingPage`：是否正在切换页码。
- `error`：最近一次操作的错误，可为空。
- `hasLoaded`：是否已成功完成首次加载。

具体模型可以按需使用 Freezed 生成。

### 5.1 数据列表语义

`items` 的含义取决于分页界面的交互方式：

- 桌面数字分页：当前选中页的数据。
- 手机无限滚动：从第一页到当前已加载页的累计数据。

这属于数据展示行为，而不是数据来源模式。

控制器必须保证同一种交互模式下的状态语义一致。

切换交互模式时，不得静默改变现有列表的含义。

### 5.2 派生状态

以下数据应尽可能根据其他状态计算，而不是重复保存：

```text
totalPages = ceil(totalCount / pageSize)
```

空数据集的总页数可以定义为 0，或者采用明确约定的界面展示值。

当总条数已知时，根据总条数判断页码是否合法。

当总条数未知时，根据加载器提供的后续数据状态判断是否可以继续翻页。

## 6. 控制器操作

公开 API 应保持精简。

建议提供：

- `initialize()`
- `refresh()`
- `loadNextPage()`
- `goToPage(page)`
- `retry()`
- `updateItem(id, update)`
- `dispose()`

只有在存在明确的业务需求时，才增加新的公开操作。

### 6.1 初始化

初始化时请求第一页。

重复调用初始化时，不应重复发起相同的首次请求，除非调用方明确要求重新加载。

首次加载应以一致的方式更新状态。

### 6.2 加载下一页

`loadNextPage()` 主要服务于无限滚动列表。

控制器需要：

1. 检查是否还有后续数据。
2. 防止相同下一页被并发重复请求。
3. 请求下一逻辑页。
4. 将结果追加到已有列表。
5. 更新页码与后续数据状态。
6. 在可恢复的追加失败时保留已有数据。

同一逻辑页不得被重复追加。

不得仅因为当前结果非空，就认定下一页一定存在。

### 6.3 跳转指定页

`goToPage(page)` 主要服务于桌面数字分页。

控制器需要：

1. 在信息充分时验证目标页码。
2. 请求目标逻辑页。
3. 替换当前页展示数据。
4. 更新当前页码和分页元数据。
5. 忽略已经被新导航请求取代的旧结果。

如果刷新后目标页越界且总条数已知，应将页码调整到最后一个有效页。

### 6.4 重试

重试应使用当前有效的请求参数，重新执行失败的逻辑操作。

控制器需要区分首次加载失败、追加失败、页面切换失败等情况。

追加失败时不得自动丢弃已经加载的数据。

页面切换失败时，不得使用空列表替换最后一个成功页面。

### 6.5 更新单条数据

可选地支持通过稳定标识更新已加载的数据项，避免为单条变化重新加载整页。

调用方必须提供稳定标识，或提供可靠的身份解析方式。

更新操作不得静默修改尚未加载的其他页面中的数据。

如果插入、删除、重新排序或字段变化会影响筛选与排序结果，通常应使相关数据快照失效，或者触发刷新。

## 7. 刷新策略

刷新数据与刷新分页状态是两个独立的职责。

底层数据刷新由应用层负责，刷新后的分页状态协调由控制器负责。

### 7.1 刷新策略

建议提供：

- `resetToFirstPage`：刷新后回到第一页。
- `preserveCurrentPage`：刷新后尽可能保留当前页。

`resetToFirstPage` 适合手机下拉刷新。

`preserveCurrentPage` 适合桌面数字分页，并且仅在原页仍然有效时保留原页。

刷新策略应由调用方或界面适配层显式配置，不应由核心层根据平台自动推断。

### 7.2 刷新流程

一次刷新操作应当：

1. 确定本次刷新策略。
2. 执行注册的应用级刷新回调。
3. 通过加载器刷新数据快照或使相关缓存失效。
4. 确定刷新后目标页码。
5. 加载目标页数据。
6. 更新总条数和后续数据状态。
7. 替换或重建当前展示数据。
8. 清除刷新状态。

对于 `preserveCurrentPage`，如果总条数减少导致原页越界，应退回最后一个有效页。

如果刷新后的数据集为空，应清空展示数据，并将当前页重置到约定的空数据状态。

如果应用级刷新回调失败，控制器应保留最后一次成功的数据，并报告刷新错误。

### 7.3 业务刷新示例

PureLive 的已关注直播间列表可能需要刷新所有已关注房间的在线状态。

Repository 负责同步直播状态，并重建或使数据快照失效。

随后分页核心重新加载目标逻辑页。

分页包不得包含直播间专用业务逻辑。

### 7.4 刷新回调的归属

刷新回调属于应用层或加载器集成层。

回调可以执行：

- 刷新远程数据。
- 重建本地数据快照。
- 使缓存失效。
- 重新查询数据库。
- 同步业务状态。
- 更新搜索索引。

刷新回调不得直接修改分页核心的内部状态。

## 8. 手机、桌面与电视端行为

### 8.1 手机无限滚动

手机适配层应支持：

- 下拉刷新。
- 接近列表底部时自动加载。
- 追加加载指示器。
- 列表结束提示。
- 追加失败后的重试。
- 防止滚动事件重复触发请求。

达到设定的加载阈值时，界面调用 `loadNextPage()`。

界面适配层不得自行实现网络分页循环。

### 8.2 桌面数字分页

桌面适配层应支持：

- 首页。
- 上一页。
- 下一页。
- 总条数已知时的末页。
- 直接选择页码。
- 修改每页条数。
- 当前页指示。
- 总条数和总页数展示。

修改每页条数后，需要重新计算页码边界。

对于修改每页条数后的行为，应明确选择保留当前可见的第一条数据，还是返回第一页，并编写相应测试。

### 8.3 Android TV 与键盘导航

电视端可以使用数字分页，也可以使用无限滚动。

D-pad 焦点管理、键盘快捷键和焦点恢复属于界面适配层。

分页核心不得依赖焦点管理。

## 9. 并发与生命周期

### 9.1 重复请求

控制器必须防止不必要的重复请求。

滚动事件连续触发时，不得对同一个下一逻辑页重复发起并发请求。

### 9.2 过期结果

当新操作取代旧操作时，旧结果不得覆盖最新状态。

例如：

- 用户先选择第 3 页，随后立即选择第 4 页。
- 刷新开始时，旧页面请求仍未完成。
- 用户更改筛选条件时，旧查询请求仍在执行。
- 控制器释放时，网络请求仍未完成。

应采用请求代次、操作标识、取消令牌或等效机制。

即使支持请求取消，也必须检查请求代次，因为取消不一定能够停止底层操作。

### 9.3 查询条件变化

搜索关键词、过滤条件、排序规则及其他决定数据集的参数，都属于逻辑数据集的身份信息。

这些参数变化时：

1. 使旧查询相关请求失效。
2. 重置或显式协调当前页码。
3. 加载新查询的数据。
4. 防止旧查询结果进入新状态。

控制器可以接收查询标识或代次，但不应拥有应用特定的过滤模型。

### 9.4 资源释放

控制器释放后：

- 不得再启动新操作。
- 未完成的旧请求不得继续发布状态。
- 控制器拥有的订阅必须取消。
- 加载器拥有的资源按照约定释放。

控制器不得释放自己并不拥有的共享 Repository。

## 10. 错误处理

发生错误时，应尽可能保留已有的有效数据。

建议行为：

- 首次加载失败：显示错误，允许重试。
- 追加加载失败：保留已加载数据，允许重试。
- 页面切换失败：保留最后一次成功的页面。
- 刷新失败：保留最后一次成功的数据，并报告错误。
- 页码无效：根据约定拒绝操作或调整页码。
- 空结果：视为合法结果，不视为错误。
- 请求取消或结果过期：不应作为当前操作的失败发布。

错误信息应在核心层之外转换为本地化界面文本。

核心层可以保留原始异常或类型化错误对象，供诊断和日志使用。

## 11. Riverpod 集成

通过适当的 Riverpod Provider 管理控制器生命周期。

Provider 应负责：

- 使用加载器和初始配置创建控制器。
- 暴露不可变分页状态。
- 在生命周期结束时释放控制器。
- 避免因无关的 Widget 重建而重复创建控制器。

当分页数据依赖查询条件、分类、用户或内容源时，可以使用 Family Provider。

Provider 的身份必须反映所有会改变逻辑数据集的关键参数。

加载器应通过依赖注入传递给控制器，而不是通过全局服务定位器获取。

分页状态模型不得包含 Flutter Widget 状态或 `BuildContext`。

## 14. 实施计划

### 第一阶段：定义数据契约

实现：

- `PaginationRequest`
- `PaginationResult`
- `PaginationState`
- `PaginationLoader`
- 刷新策略
- 分页计算工具

### 第二阶段：实现分页控制器

实现：

- 初始化。
- 页面跳转。
- 数据追加。
- 刷新。
- 重试。
- 请求代次检查。
- 生命周期管理。

### 第三阶段：接入一个远程 Repository

选择 PureLive 中一个现有功能验证加载器契约和分页状态行为。

在契约得到验证之前，不要一次性实现所有数据源适配器。

### 第四阶段：接入手机与桌面界面

让手机无限列表和桌面数字分页使用同一套控制器 API。

### 第五阶段：增加其他加载器

在各自所属的应用层或数据层中实现批次聚合、全量数据切片和本地响应式数据加载。

### 第六阶段：验证与稳定

完成单元测试、集成测试、界面测试和公共 API 审查。

除非多个实际使用场景证明有必要，否则不要增加新的抽象层。

## 15. 最终架构决策

1. 分页核心不定义数据来源模式枚举。
2. 分页核心不发起 HTTP 请求。
3. 分页核心不聚合服务端批次。
4. 分页核心不持有业务全量数据集。
5. 分页核心不执行本地数据库查询。
6. 分页核心只使用逻辑页码和逻辑每页条数。
7. 外部加载器返回已经准备好的逻辑页结果。
8. 手机与桌面共用控制器，使用不同的界面适配层。
9. 数据获取与业务刷新属于应用层。
10. 分页状态协调属于分页控制器。
11. Riverpod 负责状态暴露与生命周期集成。
12. `live_net` 与分页核心保持独立。
13. `paging_view` 仅作为设计参考，不是必需依赖。
14. 新的数据来源不应要求修改分页核心契约。

最终原则：

**业务层负责准备数据，分页核心负责管理分页，界面适配层负责呈现分页。**
