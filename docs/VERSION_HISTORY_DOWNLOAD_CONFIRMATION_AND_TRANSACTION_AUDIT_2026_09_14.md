# 版本历史下载确认与事务审计（2026-09-14）

## 范围与结论

本批复核版本历史页面从发布文件卡片进入下载确认、再交给平台下载器的完整事务。基线为 `889201e736532f4d4ad8172e73b11e27e68070ef`，实现提交为 `cdc18971fcd3c542031e0c90f30d01a7fa83ac96`。

旧弹窗只显示“是否下载？/ Do you want to download this file?”，当一个版本同时提供 APK、便携 ZIP 或安装器时，用户在最终确认阶段看不到目标文件。下载入口也没有进行中门禁，同一文件动作连续触发两次会叠加两个 `AlertDialog`；确认后下载任务尚未结束时，入口还能创建新的确认和重复下载工作。

现由版本历史页面持有单次下载事务：先按完整 HTTP(S) 合同取得规范 URI，再同步进入忙碌状态；从确认弹窗、平台下载器到错误反馈全部结束后才释放门禁。确认正文优先使用去空白后的发布文件名，空名称依次回退到 URI 最后一个有效路径段和双语“未命名文件”。下载回调仍消费同一个规范 URI，并保留原始文件名参数，既有下载器接口不变。

确认框改为可滚动 `AlertDialog`，使用 16/20 窗口边距、420 px 正文宽度上限、向下动作溢出及至少 48×48 的取消/下载操作。在 320×480、3.0 倍英文文字下，具名确认、取消和下载动作均保持可见并可命中。

## 交互合同

1. 确认正文明确显示本次将下载的文件名；缺失声明名称时使用 URL 文件名或稳定本地化占位。
2. 取消、点击遮罩或系统返回不启动下载，并释放本次事务。
3. 快速重复触发只创建一个确认路由；第一项事务持有其捕获的文件和规范 URI。
4. 用户确认后，事务门禁持续覆盖平台下载回调；回调结束前的重复动作不创建弹窗，也不增加下载调用。
5. 下载成功、失败或异常都会释放门禁；随后可重新触发新的确认事务。
6. 页面或发起详情 context 已退出时不继续下载，也不向旧页面提交反馈。
