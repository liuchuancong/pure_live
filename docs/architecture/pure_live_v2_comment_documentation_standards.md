# PureLive v2 注释与文档注释规范

> 适用范围：所有 Dart/Flutter 源码、公共 API、架构契约、扩展适配器、测试、脚本和配置。  
> 目标：注释解释意图、约束、原因和风险；不重复代码本身。注释应准确、可维护，不因 AI 重构而被随意删除。

## 1. 核心原则

1. **解释为什么，不重复做什么。** 代码已经清楚表达的操作通常不需要注释。
2. **注释必须与代码一致。** 修改行为时同步更新相关注释；过期注释比没有注释更危险。
3. **保留有效的原有注释。** 重构或 AI 修改时，不得无理由删除用户原有的设计说明、兼容性说明和 TODO。
4. **公共 API 必须有文档注释。** 包入口导出的类、枚举、方法、属性、扩展和 typedef 应说明用途、约束及重要参数。
5. **注释不能替代类型、命名和测试。** 能通过类型或结构表达的约束，优先用代码表达。
6. **安全、并发、生命周期、平台差异和兼容性必须说明。** 尤其是外部扩展、媒体播放、文件系统和异步资源。
7. **不写无意义注释。** 如 `// 设置名称` 紧挨着 `name = value;`，没有增加信息。
8. **不把临时推测写成事实。** 未验证的兼容性问题应标记为待验证，而不是断言。
9. **注释语言保持一致。** 本仓库默认中文说明设计意图；公开 API 可使用中文文档注释。专有名词、协议字段、类名和 API 名称保留原文。
10. **格式化工具不会替你判断注释质量。** `dart format` 通过不代表注释完整或正确。

## 2. 注释类型与使用场景

| 类型 | 语法 | 使用场景 |
|---|---|---|
| 文档注释 | `///` | 公共 API、类、枚举、构造函数、方法、属性、typedef、扩展 |
| 普通行注释 | `//` | 局部实现原因、算法步骤、平台差异、关键边界条件 |
| 块注释 | `/* ... */` | 仅用于确有需要的多行说明；一般优先 `//` 或 `///` |
| TODO/FIXME 等 | `// TODO(...)` | 未完成事项、已知问题、待移除兼容代码 |
| 文件头说明 | `///` 或 `//` | 仅当文件职责、生成约束或平台限制不容易从代码看出时使用 |

不要使用 HTML 注释风格，也不要在 Dart 源码中用大段星号装饰注释。

## 3. 文档注释 `///`

### 3.1 何时必须写

以下内容必须有文档注释：

- `lib/<package_name>.dart` 导出的公共类、枚举、typedef、扩展。
- 公共构造函数、工厂构造函数、公共方法和公共属性。
- 跨 package 使用的契约、模型、错误类型和接口。
- 插件/Provider 扩展点、运行时桥接 API、生命周期 API。
- 具有非直观默认值、单位、范围、线程/异步语义或平台限制的公共参数。
- 重要的配置项、策略对象和对外使用的常量。

简单、显而易见的私有 getter 不强制添加文档注释；复杂私有方法仍应解释关键意图。

### 3.2 推荐结构

```dart
/// 加载指定直播间的播放信息。
///
/// 返回当前线路可用的播放源。网络错误和解析错误会转换为
/// [LiveFailure]，调用方不应依赖底层 HTTP 异常类型。
///
/// [roomId] 是 Provider 内部的房间标识，不保证等同于平台展示 ID。
///
/// Throws:
/// - 本方法按约定返回失败结果，不通过异常表达可预期的业务失败。
```

注意：

- 第一行用一句话概括功能。
- 第二段解释行为、边界、重要约束或设计原因。
- 参数含义不直观时单独说明。
- 使用 `[TypeName]`、`[methodName]` 等可解析的 Dart 文档引用。
- 不要机械地为每个参数重复写“参数 X”。
- 若方法可能抛出异常，说明哪些异常可能出现以及原因；不要列出不可能发生的异常。
- 不要写与真实签名不符的 `Throws` 描述。Dart 文档没有强制的 throws 声明机制，文案应以实际实现为准。

### 3.3 类与接口示例

```dart
/// 执行扩展请求并返回统一的运行结果。
///
/// 所有请求都必须经过 [ExtensionGateway]，以应用超时、权限和日志脱敏策略。
/// 实现不得绕过宿主的请求策略直接访问网络。
abstract interface class ExtensionExecutor {
  /// 执行一次扩展操作。
  ///
  /// [cancellationToken] 在调用方取消或扩展被卸载时触发。
  Future<ExtensionResult> execute(
    ExtensionRequest request, {
    required CancellationToken cancellationToken,
  });
}
```

### 3.4 不合格示例

```dart
/// 获取房间。
Future<Room> getRoom(String id) async {
  return repository.getRoom(id);
}
```

如果 API 语义确实只等同于方法名，这种注释几乎没有帮助。应补充缓存、失败、ID 语义或生命周期等真实约束；若没有额外信息，优先使用清晰命名而不是凑字数。

## 4. 普通实现注释 `//`

普通注释重点解释**原因、约束和非显然行为**。

### 适合写注释

```dart
// 该站点要求先获取页面 Cookie，再请求播放地址；不能与通用请求合并。
final cookie = await fetchSiteCookie();


// 这里必须先取消旧任务再切换线路，避免旧任务的失败回调覆盖新状态。
await cancelCurrentTask();
await switchLine();
```

### 不适合写注释

```dart
// 获取 Cookie
final cookie = await fetchSiteCookie();

// 将索引加一
index++;
```

### 算法分段注释

当算法包含多个阶段、回退策略或容易误改的顺序时，可以按步骤注释：

```dart
// 1. 优先尝试当前线路。
// 2. 当前线路失败后尝试同源备用线路。
// 3. 同源线路耗尽后才切换播放引擎。
// 4. 所有策略耗尽后进入带退避的等待状态。
```

只有当代码确实按此顺序执行时才保留这类注释。更复杂的恢复策略应优先拆成命名明确的方法，并配套测试。

## 5. 注释放置规则

- 注释放在它解释的声明或语句之前。
- 不要把注释放在很远的位置，让读者无法确定对应对象。
- 少用行尾注释；仅用于短小且不影响阅读的局部说明。
- 复杂条件优先提取为有意义的变量或方法，而不是给超长条件写一段注释。
- 对字段单位、范围和特殊语义，可使用文档注释或清晰命名，例如 `timeoutDuration`、`maxResponseBytes`。
- `// ignore:`、`// ignore_for_file:`、`// coverage:` 等工具指令必须紧邻生效代码，并解释必要的例外原因。
- 不允许用注释掉的旧代码代替 Git 历史。删除失效代码；若必须暂留，应说明删除阻碍与移除条件。

## 6. TODO、FIXME、HACK、NOTE 规范

统一格式：

```dart
// TODO(owner): 明确的待办事项；说明完成条件。
// FIXME(owner): 已知错误及触发条件。
// HACK(owner): 临时绕过方案及移除条件。
// NOTE: 影响维护者理解的重要约束。
```

规则：

- `TODO` 必须描述可执行的后续工作，不能只写“优化一下”。
- `FIXME` 必须说明错误表现或风险；最好附 issue 链接或编号。
- `HACK` 必须说明为什么暂时需要、风险是什么、什么条件下可以移除。
- `NOTE` 用于非显然的约束，不应被滥用。
- 不知道负责人时可以使用 `TODO:`，但应在关联 Issue 或文档中明确责任归属。
- 不要写虚构的 issue 链接或未经确认的日期。
- 发布前应检索新增的 `TODO`、`FIXME`、`HACK`，确认它们被记录或有明确理由。

示例：

```dart
// TODO(#184): 等扩展协议 v2 发布后移除旧字段兼容逻辑。
```

如果项目没有使用 GitHub Issue 编号，则使用仓库实际采用的问题跟踪标识，不要强制使用 `#123`。

## 7. 文件头注释

默认不要求每个 Dart 文件写一段重复的文件头注释。以下情况建议添加：

- 文件实现平台专属逻辑。
- 文件承载复杂协议解析或状态机。
- 生成器对文件有特殊要求。
- 文件存在重要的资源生命周期或安全边界。
- 文件内容不能通过文件名和类型结构快速理解。

示例：

```dart
/// drpy 请求桥接。
///
/// 此适配器保留脚本侧同步请求语义；运行时若只能提供异步请求，
/// 必须通过受控兼容策略处理，不能静默改变返回类型。
```

不要把个人署名、当前日期或容易过期的版本号作为无必要的文件头内容。

## 8. 注释语言与术语

- 设计原因、边界和维护说明默认使用简体中文。
- API 名称、类名、参数名、协议字段、命令和错误码保留原文。
- 首次出现缩写时，若团队成员可能不熟悉，应写出全称或简短解释。
- 同一概念使用统一术语，例如“扩展（Extension）”“宿主（Host）”“能力（Capability）”“播放线路（Line）”。
- 不要中英混杂地重复表达同一句话。
- 不要将用户可见文本写进源码注释后期待 UI 显示；用户可见内容必须走本地化系统。

## 9. 需要重点注释的场景

### 9.1 安全边界

必须说明信任边界、授权原因和限制条件：

```dart
/// 校验扩展可访问的目标地址。
///
/// 该校验用于阻止扩展访问未授权的本地/私网资源；重定向后的目标
/// 也必须重新校验，不能只验证最初的 URL。
```

不要在注释中写真实令牌、Cookie、用户隐私或敏感内部地址。

### 9.2 并发与异步

对锁、队列、任务取消、去重、重试和状态竞态写明原因：

```dart
// 使用 generation 标识丢弃过期请求的结果，避免慢请求覆盖较新的状态。
final requestGeneration = ++_generation;
```

### 9.3 生命周期与资源所有权

说明谁创建、谁释放、何时取消：

```dart
/// 此订阅由当前 Controller 持有，并在 [dispose] 中取消。
late final StreamSubscription<PlayerEvent> _subscription;
```

### 9.4 平台差异

说明差异、受影响的平台和回退行为；不要只写“兼容问题”。

```dart
// 某些桌面平台不支持系统级目录选择；不支持时返回明确的能力错误，
// 不回退到未经授权的硬编码路径。
```

### 9.5 兼容性代码

解释为什么保留旧行为、兼容哪个协议版本，以及移除条件：

```dart
// 旧版源仍使用 `url` 字段；仅在新字段缺失时读取，迁移完成后移除。
```

### 9.6 单位和魔法数字

优先提取有意义的常量：

```dart
static const Duration requestTimeout = Duration(seconds: 15);
static const int maxManifestBytes = 2 * 1024 * 1024;
```

如数字体现协议规定或经过测量的边界，应说明依据：

```dart
// 与上游协议限制保持一致；调整前需同步更新契约测试。
static const int maxEntries = 5000;
```

不要只写 `// 15 秒`；应使用有意义的常量名，注释只补充原因。

## 10. 公共契约与数据模型注释

公共模型需要解释字段语义、单位、可空含义和兼容性，而不是简单复述类型。

```dart
/// 可播放媒体资源。
class MediaResource {
  /// 可交给播放器的媒体 URI。
  ///
  /// 可能是直链、代理 URI 或平台专属 URI；调用方不得假设它一定是 HTTP。
  final Uri uri;

  /// 资源有效期；未知或不受支持时为 `null`。
  final DateTime? expiresAt;

  /// 播放资源的请求头。
  ///
  /// 不得写入普通日志；传递到播放器前应遵循资源所属扩展的权限策略。
  final Map<String, String> headers;
}
```

规则：

- `null` 的含义必须明确：未知、缺失、不适用还是无限期。
- 时间统一说明时区和精度。
- 数值统一说明单位。
- ID 说明来源和稳定性。
- URL/URI 说明是否可能带认证信息或过期签名。
- 序列化字段有兼容性要求时，记录旧字段和迁移策略。
- 公共枚举新增值时，说明调用方如何处理未知值。

## 11. 测试代码注释

测试名应优先描述行为：

```dart
test('取消旧请求后，旧结果不会覆盖新线路状态', () async {
  // Arrange / Act / Assert 仅在测试逻辑较复杂时使用注释分段。
});
```

- 不为每个简单测试机械添加 `// Arrange`、`// Act`、`// Assert`。
- 对不直观的 fixture、模拟竞态或安全输入解释其代表的真实场景。
- 注释不能替代断言。
- fixture 说明数据来源、脱敏状态和覆盖的兼容行为。
- 不在测试注释里承诺未实际验证的平台行为。

## 12. 禁止事项

禁止以下注释习惯：

1. 注释与代码完全重复。
2. 复制整段代码到注释里解释。
3. 注释声称做了安全检查，但代码没有执行检查。
4. 修改实现后不更新相应注释。
5. 用大量装饰性分隔线淹没文件主体。
6. 把整段旧实现注释掉留在文件里。
7. 无原因删除原有有效注释。
8. 添加虚假的 TODO、issue 编号、链接或测试结果。
9. 用“兼容所有平台”“绝对安全”“永不失败”等无法证明的绝对化描述。
10. 在注释中记录凭据、私人数据或敏感 URL。
11. 用注释替代明确命名、类型约束或测试。
12. 为每个简单语句都加注释，降低代码可读性。

## 13. AI 修改代码时的注释规则

AI 编码代理必须遵循：

- 修改前阅读相关注释、README、契约和 ADR。
- 默认保留用户原有有效注释。
- 不因重写方法、格式化代码或“优化风格”而批量删除注释。
- 如果注释已过期，必须根据新行为更新，而不是原样保留错误说明。
- 删除注释时，应确认它没有记录安全约束、兼容行为、性能原因或历史决策。
- 新增复杂逻辑时补充解释原因、边界和失败路径，不为简单赋值补注释。
- 修改公共 API 时同步更新文档注释和使用示例。
- 不确定注释描述的行为时先检查实现、测试或上游资料，不凭猜测改写。
- 交付说明中指出注释是否有更新；如果保留了暂时无法验证的说明，应明确列出。

## 14. 注释检查清单

代码提交前检查：

- [ ] 新增的公共 API 是否有准确的 `///` 文档注释。
- [ ] 注释解释的是原因、边界或约束，而不是重复代码。
- [ ] 注释与当前实现、测试和契约一致。
- [ ] 安全、权限、并发、取消和资源释放行为是否有必要说明。
- [ ] TODO/FIXME/HACK 是否明确、可追踪且没有虚构信息。
- [ ] 是否误删了原有有效注释。
- [ ] 是否遗留整段注释掉的旧代码。
- [ ] 是否有敏感信息或过度承诺。
- [ ] 文档引用的类型和方法是否存在。
- [ ] 注释语言和项目术语是否统一。

## 15. 可复制的注释模板

### 公共类

```dart
/// <该类型负责的核心职责>
///
/// <重要的行为约束、边界或设计原因>
/// <必要时说明线程/异步、生命周期、安全或平台限制>
class Example {
  // ...
}
```

### 公共方法

```dart
/// <一句话描述方法行为>
///
/// <说明失败语义、缓存/副作用、边界条件或重要约束>
///
/// [parameter] <仅在参数含义不直观时说明>
Future<Result> execute(Parameter parameter) async {
  // ...
}
```

### 临时兼容逻辑

```dart
// NOTE: <当前必须保留该逻辑的原因>。
// TODO(<issue-or-owner>): <可验证的移除条件>。
```

### 平台差异

```dart
// <平台/版本> 存在 <具体差异>。
// 当前使用 <回退策略>；不支持时返回 <明确结果>。
```

## 16. 最终原则

**注释的价值在于保存代码无法直接表达的知识。**  
公共 API 写清契约；复杂实现写清原因；安全和生命周期写清边界；临时兼容写清移除条件。其他地方尽量让代码通过命名、类型和测试自行说明。
