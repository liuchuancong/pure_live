# PureLive v2 项目开发规范

> 本文是 PureLive v2 的仓库级开发规范，适用于应用、基础设施、生态适配器、Provider、Feature、UI 和平台实现。  
> 目标：模块可独立开发、依赖方向稳定、AI 与人工贡献遵循同一规则、代码可测试、升级可控。

## 1. 规范优先级

当规范冲突时，按以下优先级处理：

1. 安全、隐私与平台政策。
2. 本文的架构不变量。
3. `architecture/` 下的架构决策记录（ADR）及对应架构规范。
4. `contracts/` 下的公开契约。
5. 本文的编码与测试规范。
6. 局部实现习惯。

若确需改变高优先级规则，先新增或更新 ADR，再修改代码；不得通过局部实现悄悄绕过架构约束。

## 2. 仓库结构与模块职责

推荐结构：

```text
apps/
  pure_live/                 # 应用入口与唯一组合根

packages/
  foundation/                # 日志、网络、路径、存储、缓存、诊断等
  integrations/              # 外部基础能力集成，如媒体引擎
  ecosystem/                 # 平台契约、插件系统、运行时、权限、能力等
  services/                  # 搜索、收藏、历史、下载、备份等跨 Feature 服务
  providers/                 # 直播、音乐、TVBox、IPTV 等内容/协议实现
  features/                  # home、live、vod、music、search、settings 等功能
  ui/                        # design tokens、Wind、adaptive、player UI 等

third_party/                 # 上游源码镜像及最小必要补丁
fixtures/                    # 跨包测试样本
tool/                        # 仓库脚本、校验与脚手架
docs/                        # 架构、规范、ADR、迁移和发布文档
```

### 2.1 `apps/pure_live`

- 是唯一应用组合根，负责初始化日志、配置、依赖注入、路由、主题、本地化和平台能力。
- 负责将各 package 组合为可运行应用。
- 不放可被其他模块复用的业务实现。
- 不允许其他 package 反向依赖 `apps/pure_live`。

### 2.2 `foundation`

- 提供稳定、通用、尽量与业务无关的基础能力。
- 例如 network、filesystem、storage、logging、diagnostics、cache、localization。
- 不依赖 Feature、Provider 或应用入口。
- 不承载直播、音乐、视频等领域规则。

### 2.3 `ecosystem`

- 定义插件契约、扩展生命周期、能力、权限、身份、任务、运行时和外部生态适配规则。
- 契约模型尽可能使用纯 Dart，不依赖 Flutter UI。
- 不直接依赖具体 Feature 页面。
- 具体扩展运行时通过 Adapter 接入，不把运行时内部 API 泄漏到公共契约。

### 2.4 `providers`

- 负责特定内容源、站点协议或外部生态的实现。
- Provider 不直接操作页面、弹窗或全局 UI 状态。
- Provider 通过公开契约访问网络、存储、权限、任务和媒体能力。
- 不同 Provider 不得相互直接依赖；需要共享代码时抽到稳定的公共模块。

### 2.5 `features`

- 负责用户可见的业务体验、页面状态与交互。
- 通过 Repository、Service、Use Case 或公开契约访问业务能力。
- 不直接依赖第三方站点私有协议实现。
- 不重复实现 Network、FileSystem、Notice、Dialog 等基础设施。

### 2.6 `ui`

- 提供 Design Tokens、Wind 统一组件、响应式布局、主题解析和平台 UI 适配。
- Feature 优先依赖项目级 UI 门面，不直接耦合六种视觉风格的具体实现。
- 不依赖具体业务 Feature 或 Provider。

## 3. 架构不变量

以下规则必须通过代码审查或自动化工具持续检查：

1. `apps/pure_live` 是唯一组合根。
2. 依赖方向由应用/Feature 指向契约和服务，不允许底层模块反向依赖上层。
3. `foundation` 不依赖 `features`、`providers`。
4. `providers` 不依赖具体页面或其他 Provider。
5. `features` 不直接依赖第三方脚本运行时的内部 API。
6. UI 只通过统一门面调用通知、对话框、加载和主题能力。
7. 外部扩展、外部配置和网络响应均视为不可信输入。
8. 插件能力必须经过明确授权；禁止隐式共享 Cookie、令牌或文件权限。
9. 媒体解析、媒体资源、播放引擎与播放器 UI 分层。
10. 缓存、用户数据、凭据与可恢复备份必须分开管理。
11. 跨包公共 API 的变更必须更新契约测试和文档。
12. 不允许为绕过编译错误而添加无边界的 `dynamic`、空实现或吞异常逻辑。

## 4. Dart Pub Workspace 与依赖管理

- 使用 Dart Pub Workspace 作为 monorepo 的工作区和依赖解析基础。
- 根 `pubspec.yaml` 统一声明 workspace members；成员 package 使用 `resolution: workspace`。
- Melos 可用于脚本编排，但不得维护第二份与 Pub Workspace 不一致的 package 列表。
- 内部 package 命名统一使用 `pure_live_<name>`，目录名使用短名称，并保持一一映射。
- `pubspec.lock` 按应用仓库策略提交并纳入 CI 检查。
- 禁止随意使用 Git `main`、未固定分支或未经审查的 path override 作为长期依赖。
- 对 Git 依赖必须记录仓库、固定 commit/tag、原因和升级策略。
- 引入依赖前检查维护状态、许可证、Dart/Flutter 约束、目标平台、传递依赖和安全风险。
- 避免职责重叠的库并存，例如多个状态管理框架、多个 HTTP 引擎或多个 Toast 系统。
- 生产代码不得依赖仅用于测试的 package。
- 任何新增依赖必须说明为何不能用现有能力完成。

## 5. 文件与 package 结构

每个 package 至少应包含：

```text
package_name/
  pubspec.yaml
  README.md
  CHANGELOG.md
  lib/
    package_name.dart
    src/
  test/
```

规则：

- `README.md` 必须写清职责、公开入口、允许依赖、禁止依赖、使用示例和平台限制。
- `CHANGELOG.md` 记录可感知变化、迁移要求和破坏性变更。
- 公共 API 通过 `lib/<package_name>.dart` 导出。
- 实现细节放在 `lib/src/`，其他 package 不得 import 对方的 `src/`。
- 不为了形式拆包。一个模块先在现有 package 内建立清晰目录；当出现第二个稳定消费者、职责明显独立或维护边界明确时，再通过 ADR 评估拆包。
- package 目录名、pub package 名、导入前缀和 README 中的名称必须一致。
- 每个公开 API 都要有文档注释；内部实现按复杂度添加必要注释。

## 6. 编码与格式规范

### 6.1 格式化

- 使用仓库统一的 Dart/Flutter SDK 版本与 `dart format`。
- 保存格式由项目 formatter 配置和编辑器设置决定，不依赖个人机器的默认设置。
- 提交前运行：

```bash
dart format --set-exit-if-changed .
flutter analyze
flutter test
```

- CI 格式检查失败即视为检查未通过。
- 不通过手动对齐空格、随意换行或个人风格覆盖 formatter。
- 不在一次无关功能修改中全仓格式化，除非任务明确要求或单独提交格式化变更。

### 6.2 命名

- 类型：`UpperCamelCase`。
- 变量、方法、参数：`lowerCamelCase`。
- 文件、目录：`snake_case.dart`。
- 常量遵循 Dart 常规 `lowerCamelCase`，除非仓库现有规范明确采用其他形式。
- 布尔值优先使用 `is`、`has`、`can`、`should`、`enable` 等语义明确的命名。
- 避免无意义缩写；协议和生态常用缩写可保留，例如 IPTV、M3U、TVBox。
- 私有实现使用 `_`，不要为了绕过可见性限制而暴露内部类。

### 6.3 类型与空安全

- 禁止新增无必要的 `dynamic`。
- 禁止通过 `!` 随意压制空安全问题；必须证明值在此处非空，并优先用局部校验或类型建模表达。
- 避免 `Map<String, dynamic>` 在多个层之间传播；在边界处转换成类型化模型。
- 不把外部 JSON 直接视为可信业务模型。
- 避免过度使用 `as` 强制类型转换。
- `final` 优先用于不需要重新赋值的局部变量和字段。
- 不可变模型优先；需要修改时明确状态所有权。

### 6.4 异步与资源生命周期

- 不在 UI `build()` 中启动网络、文件或播放器等副作用。
- 不创建无人管理的 Future。
- 资源创建者负责释放：StreamSubscription、Timer、Controller、FocusNode、AnimationController、Dio 资源等。
- 需要时使用 `try/finally` 保证释放。
- 异步任务必须定义取消、超时和页面销毁后的处理规则。
- 不通过 `Future.delayed` 作为缺乏生命周期管理的状态同步方案。
- 禁止忽略异步异常；后台任务必须进入统一日志/诊断系统。

### 6.5 异常与结果

- 不使用空 `catch`。
- 不用 `catch (_) {}` 掩盖失败；若确实允许忽略，必须有注释说明理由。
- 在边界层把底层异常映射为稳定错误模型。
- 业务层按统一规范使用 `Either<Failure, T>` 或 `Future<Either<Failure, T>>`；只有在确有异步组合价值时使用 `TaskEither`。
- Riverpod `AsyncValue` 用于 UI 异步状态，不作为业务错误模型的替代品。
- 禁止多层重复包装同一种成功/失败结果。
- 错误信息供用户显示前必须经过本地化和敏感信息过滤。

## 7. 网络规范

- 所有 HTTP 请求通过 `foundation/network` 的统一入口创建客户端。
- 不允许 Feature 或 Provider 任意 `Dio()`，除非通过网络模块的注册工厂。
- 按用途区分 API、Extension、Media/Download、Update 客户端策略。
- 拦截器必须可测试，且不得在日志中泄露认证头、Cookie、令牌、签名 URL 或个人数据。
- 请求超时、取消、重试、缓存和代理策略必须显式定义。
- 只对符合幂等规则的请求自动重试。
- 外部扩展的 Cookie、请求头、代理和凭据按扩展隔离。
- 不把应用认证令牌自动注入扩展请求。
- 对外部 URL 和重定向执行 SSRF、私网地址、协议与目标主机检查。
- 下载写入临时文件；完成大小和校验检查后再原子替换。
- 测试使用 fake adapter/mock server/fixture，不依赖真实站点作为常规单元测试前提。

## 8. 文件系统与持久化规范

- 路径拼接统一使用 `package:path`，禁止硬编码 `\\` 或 `/` 作为跨平台路径分隔符。
- 系统目录通过 `path_provider` 获取，不猜测系统目录。
- 用户可选文件通过文件选择器和平台授权流程访问。
- 用户数据、缓存、临时文件、凭据分开存储。
- 缓存可以重建；用户数据不能因缓存清理被删除。
- 简单非敏感偏好使用 `shared_preferences`；结构化数据使用数据库；凭据使用安全存储。
- 不将大量结构化业务数据放入 SharedPreferences。
- 重要文件使用“临时写入 → flush/校验 → 原子替换”的流程；跨平台原子性能力需要按平台验证。
- 数据库迁移必须可测试；迁移失败不能静默删除旧数据。
- 备份必须有格式版本、完整性校验、恢复前预检和失败处理。
- 不在日志中输出完整本地路径中可能包含的用户名、令牌或敏感文件名。

## 9. UI、主题与布局规范

### 9.1 统一 UI 入口

- Feature 默认使用 `flutter_sdk_wind` 提供的项目级组件。
- 不允许在各 Feature 中自行封装重复的按钮、输入框、Dialog、Toast、Loading、空状态。
- 具体平台风格包只允许由 `ui` 适配层直接依赖。
- 主题、组件语义、颜色、间距、圆角、动效和焦点样式集中定义。
- 引入新的 UI 库前先检查 Wind 是否已有对应组件。

### 9.2 六种风格

目标风格为 Material、Cupertino、Fluent、macOS、Neumorphic、Yaru。

- 使用统一 Theme Resolver 选择风格。
- 每种风格只负责组件表现，不得改变业务行为和领域模型。
- 某个风格或平台不支持某组件时，使用有文档的回退实现。
- 不能只根据操作系统自动锁定风格；允许用户选择。
- 新增或升级风格包必须通过目标平台构建、深浅色、文本缩放、键盘焦点、TV D-pad 和可访问性检查。
- 不承诺任何未经实际验证的库完整支持六个平台。

### 9.3 响应式布局与尺寸

- 使用 `LayoutBuilder`、`MediaQuery` 和设计断点决定布局。
- `flutter_screenutil_plus` 只用于确有必要的设计稿尺寸适配，不替代响应式布局。
- 文本缩放、容器尺寸和图标尺寸分别管理。
- 禁止对同一尺寸重复应用 `.sp`、自定义 scale 和系统文本缩放。
- 禁止尺寸 getter 相互调用造成递归。
- 手机触摸、桌面鼠标键盘、TV 遥控器使用不同的交互尺寸与焦点策略。
- TV 界面必须验证焦点可见性、焦点顺序、边缘导航、返回键和遥控器确认键。

### 9.4 弹窗与通知

- 通过 Wind/AppDialog、AppNotice、AppLoading 等项目门面调用。
- 业务层不得直接依赖 `toastification` 等具体通知包。
- 同一页面应避免多个互相遮挡的通知或重复弹窗。
- 弹窗必须有明确关闭行为、键盘/D-pad 焦点管理和可访问性语义。
- 长任务优先使用进度状态而非频繁 Toast。
- 错误通知应提供可行动信息，详细诊断写入日志而非直接展示堆栈。

## 10. 状态管理与路由

- 使用 Riverpod 作为项目主要状态管理和依赖注入方案。
- 不引入第二套全局状态管理框架。
- Provider 的职责、生命周期和缓存策略必须清楚。
- 纯业务状态与 Widget 局部交互状态分开；不把每个局部布尔值都提升为全局 Provider。
- 路由通过 `go_router` 统一定义，避免散落字符串路径。
- 深链接、认证守卫、未知路由和返回行为必须测试。
- 路由层不承载复杂业务规则。
- 页面销毁后不得继续更新已销毁的 UI 或持有无主资源。

## 11. 模型、序列化与外部数据

- 内部模型与外部协议 DTO 分离。
- 外部字段先解析、验证，再转换为领域模型。
- `freezed` / `json_serializable` 负责生成模型代码，不代替运行时安全校验。
- 对外部数据限制最大字节数、数组长度、嵌套深度和字符串长度。
- 解析失败返回可诊断的错误，不得默默构造貌似有效的默认对象。
- 对协议兼容行为建立 fixtures 和回归测试。
- 修改公共模型时同步更新序列化测试、契约测试和迁移说明。

## 12. 扩展与插件安全规范

- 第三方脚本、导入配置和远程扩展默认不可信。
- 扩展必须通过 Extension Gateway 执行。
- Feature 不直接调用 fjs 或其他 Runtime 内部 API。
- 扩展必须有 ID、版本、来源、能力声明和信任状态。
- 权限按能力逐项授予；默认拒绝不必要的文件、网络、凭据和跨扩展访问。
- 对执行时间、并发数、内存/输入输出大小、请求数量和下载大小设限。
- 运行时失败应隔离并可恢复，不得拖垮主 UI。
- 扩展日志必须带扩展 ID 与请求关联 ID，并脱敏。
- TVBox/JAR/压缩包导入需要限制文件大小、条目数、目录深度，并防止路径穿越。
- 对同步 `req`、Promise、回调、二进制数据、Cookie、加密和压缩等兼容行为建立独立适配测试。

## 13. 媒体模块规范

- 媒体源、资源解析、媒体摄取、播放引擎和播放器 UI 分层。
- Feature 不直接依赖具体播放器 SDK 的内部对象。
- 通过 `media_core` 的稳定接口管理播放会话、播放状态、错误和恢复策略。
- 播放引擎能力通过能力声明/探测表达，不通过散落的 `if (platform == ...)` 复制逻辑。
- 不为所有媒体强制走 FFmpeg；仅在明确需要的转换、探测或处理场景引入。
- 播放恢复必须防止无限重试，具备次数限制、退避和可取消能力。
- 播放器、计时器、订阅和原生资源必须有清晰生命周期。
- 多窗口/多播放器并发必须定义资源预算和降级策略。

## 14. 测试规范

### 14.1 测试层次

1. **Unit Test**：纯逻辑、模型转换、错误映射、解析器。
2. **Contract Test**：跨 package 公共 API、Provider 与 Host/Runtime 交互。
3. **Fixture Test**：TVBox、M3U、音乐源、站点响应、错误响应。
4. **Widget Test**：组件状态、交互、主题、无障碍语义。
5. **Integration Test**：登录、导入、播放、下载、备份/恢复等关键流程。
6. **Platform Build Test**：Android、iOS、Windows、macOS、Linux 的实际构建能力。
7. **Golden Test**：仅对稳定且有价值的视觉关键路径使用。

### 14.2 必须测试的失败场景

- 网络超时、取消、断网、限流、服务器错误。
- 空响应、错误 JSON、字段缺失、异常大响应。
- 文件权限拒绝、磁盘空间不足、下载中断、校验失败。
- 数据库迁移失败与旧版本数据。
- 插件超时、运行时异常、恶意/畸形输入。
- 深色模式、文本放大、窄屏、桌面窗口缩放。
- TV 遥控器焦点、返回键、焦点边缘行为。
- 主题切换期间的状态保持和弹窗行为。

### 14.3 测试数据

- 测试必须可重复，不依赖不稳定的真实直播站点。
- 外部协议使用脱敏 fixture。
- fixture 不得包含真实令牌、Cookie、个人信息或有效的签名 URL。
- 修复线上问题时尽可能新增能复现问题的回归测试。

## 15. 日志、诊断与隐私

- 统一日志入口，不在生产代码散布临时 `print`。
- 日志等级与用途明确：debug、info、warning、error。
- 错误包含模块、操作、关联 ID、可恢复性和必要的上下文。
- 不记录密码、令牌、完整 Cookie、授权头、私密查询参数和用户文件内容。
- 诊断上报应可配置，并遵循产品隐私策略与用户授权。
- 外部脚本日志必须限制大小和频率，防止日志洪泛。
- 日志记录失败本身不能导致业务崩溃。

## 16. 本地化规范

- 使用 `easy_localization` 和 JSON 翻译资源。
- 应用 UI 文本不得直接散落硬编码用户可见字符串。
- 统一 key 命名，如 `common.save`、`live.room.title`、`settings.theme.title`。
- 同一 key 在各语言文件中保持一致；CI 检查 JSON 语法、缺失键和多余键。
- 不翻译、不重写用户导入的外部内容、直播标题、音乐源元数据或第三方脚本输出。
- 错误模型保存稳定 code/参数，展示层负责本地化。

## 17. 代码生成与生成文件

- 明确记录使用的生成器及生成命令。
- 修改 Freezed、JSON、Retrofit 等源定义后必须重新生成代码。
- CI 检查生成文件是否与源定义一致。
- 不手动修改生成文件，除非上游工具明确要求并有可重复流程。
- 生成文件是否提交仓库，按 package 类型统一决定，不允许同类 package 各自随意处理。
- 对生成器版本升级先在独立变更中验证。

## 18. Git 与提交规范

推荐提交格式：

```text
feat(live): add room history
fix(network): handle request cancellation
refactor(theme): centralize color tokens
test(tvbox): add parser fixtures
docs(architecture): clarify extension boundary
build(deps): update dio
```

要求：

- 一次提交尽量只做一个逻辑主题。
- 不把大规模格式化与业务修复混在一起。
- 不提交密钥、`.env`、私有源配置、构建产物和本机路径。
- 新增或修改配置样例时使用虚构凭据。
- 破坏性 API 变更必须更新调用方、测试、CHANGELOG 和迁移文档。
- 不使用 `--no-verify` 等方式绕过必需检查，除非有明确故障记录和授权的临时例外。

## 19. AI 编码代理规范

AI 代理在修改前必须：

1. 阅读仓库根目录的 `AGENTS.md` 和相关目录的局部 `AGENTS.md`。
2. 阅读目标模块 README、相关 contracts 和 ADR。
3. 查找现有实现与调用方，不重复创建已有能力。
4. 确认允许修改范围、公共 API 影响和依赖方向。
5. 先提出最小改动方案；涉及架构不变量时先更新 ADR。

修改过程中：

- 保留原有有效注释，不随意删除用户注释。
- 不擅自大规模重命名、格式化或重构无关文件。
- 不引入未经批准的依赖或新框架。
- 不使用假实现、空 catch、硬编码秘密或未经验证的 API。
- 需要变更公共契约时同步更新契约、适配器、fixture 和测试。
- 不确定的库 API 必须查阅当前项目锁定版本的源码或文档，不凭记忆编造。

完成前：

- 运行与变更范围匹配的 formatter、analyzer 和测试。
- 报告实际执行的命令、结果和未执行项。
- 列出修改文件、行为变化、风险和迁移要求。
- 不声称测试通过，除非实际运行并确认通过。
- 如果无法运行构建或测试，明确说明原因与残余风险。

## 20. 依赖升级规范

- 核心依赖升级单独提交或单独 PR。
- 升级前检查 changelog、breaking changes、最低 SDK、平台支持和传递依赖。
- 升级后执行分析、单元测试、关键集成测试和目标平台构建。
- 关键依赖升级必须验证应用启动、路由、主题、网络、文件存储和媒体播放。
- Git 依赖固定到经过验证的 tag 或 commit。
- 不为追逐“最新”而自动升级所有依赖；优先安全修复、兼容性和真实需求。
- 对弃用 API 建立迁移计划，不在新代码中继续扩散。

## 23. 最终原则

- 先找已有模块，再决定是否新建。
- 先定义契约，再实现适配器。
- 先明确数据和资源生命周期，再写异步逻辑。
- 先处理安全边界，再开放扩展能力。
- 用原生能力能解决的问题，不轻易增加依赖。
- 用成熟库能解决的问题，不重复造轮子。
- 公共能力统一封装，业务模块保持独立。
- 架构规则必须能被测试、工具或代码审查验证，而不是只写在文档里。
